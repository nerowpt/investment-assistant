## 2026-05-15 项目启动

### 起源
基于此前数次关于个人投资逻辑巡检的深度对话，决定将"投资分析"系统化为一个长期演进的产品。

### 第一轮决策（产品基础形态）

| 编号 | 问题 | 选项 | 决策 |
|---|---|---|---|
| Q1 | 用户范围 | 仅自己 / 自己+亲友 / SaaS / 开源 | **仅自己用** |
| Q2 | 部署形态 | CLI / 本地Web / 云Web / App / 多前端 | **后端 + 多前端**（CLI/Web/App，后端 API 统一） |
| Q3 | AI 角色 | 汇总 / 深度分析 / 信号 / 自动执行 | **深度分析协作者**（联网、判逻辑、给场景测算） |
| Q4 | MVP 范围 | 巡检 / 选股 / 买点 / 卖点 / 待定 | **待 PM 给推荐后确认** |

### 第二轮决策（数据、AI、协作）

| 编号 | 问题 | 选项 | 决策 |
|---|---|---|---|
| Q5 | 数据策略 | 免费 / 低付费 / 中付费 / 混合 | **混合**：免费结构化数据 + AI/Web Search 抓实时叙事 |
| Q6 | 投资周期 | 长线 / 长+波段 / 波段 / 全周期 | **长线为主 + 部分仓位做热点轮动** |
| Q7 | AI 接入方式 | API Key / 本地LLM / Cursor代理 / 多模型 | **复用 Cursor / Claude Desktop（MCP 协议）** |
| Q8 | 交互模式 | 对话 / 仪表盘 / 报告 / 混合 | **混合**：仪表盘 + 对话 + 主动推送 |

### 关键架构判断（基于 Q7）

> 因为选了 Cursor MCP 而不是自带 API Key，**产品本质是"给 LLM 用的工具集"，而不是"套了 LLM 的应用"**。
>
> 这意味着：
> 1. 后端不直接调用 LLM API，节省 token 成本
> 2. 后端实现为 MCP Server，把"取财报""算估值""跑巡检""读持仓"等能力暴露为 MCP Tools
> 3. AI 在 Cursor / Claude Desktop 里调用这些工具完成深度分析
> 4. Web UI 提供仪表盘视图，CLI 提供脚本化入口，App 提供推送通知

### 第三轮决策（MVP 范围、技术栈基线）

| 编号 | 问题 | 决策 |
|---|---|---|
| Q9 | MVP 范围 | **「持仓管理 + 逻辑巡检 + 热点扫描」**（长短双引擎，比 PM 原推荐多一个热点扫描模块） |
| Q10 | 编程语言 | **混合：Python 做数据采集/分析，Go 做后端 API + MCP Server** |
| Q11 | 持仓数据来源 | **手动维护 YAML/CSV 文件** |
| Q12 | 阶段 1 收尾方式 | 用户先审阅 v0.1 定位文档 → 反馈后再进入阶段 2 |

### 关键架构判断（基于 Q10）

> 选用 Python + Go 混合，意味着系统会有**两个进程层**：
>
> 1. **Python 数据/分析层**（`data-worker`）：调用 AKShare/Tushare、爬虫、跑财务计算、与 Web Search 协作
> 2. **Go 后端层**（`core-server`）：暴露 RESTful/gRPC API + MCP Server + 调度器 + 持仓状态管理
>
> 二者通过 **本地 RPC**（gRPC 或 HTTP）通信。Python 不直接对外暴露端口，所有外部入口（CLI/Web/MCP）走 Go。
>
> **优点**：Python 拿 pandas/AKShare 生态红利，Go 拿强类型/稳定性红利；分工清晰
> **代价**：双语言项目，需要管两个依赖系统（Poetry/uv + Go modules），需要进程间通信契约

### 关键范围调整（基于 Q9）

> 原 PM 推荐 MVP = 「持仓管理 + 巡检」（纯长线）
> 用户要求 MVP = 「持仓管理 + 巡检 + 热点扫描」（长短双引擎）
>
> **影响**：
> - 数据采集层需要新增"热点话题/题材"采集器（如东财涨停板、雪球热度榜、淘股吧/股吧热帖）
> - AI 工具集需要新增"热点 → 受益标的关联""短线弹性评估"工具
> - MVP 工期会从原计划的 4-6 周扩展到 6-8 周
> - 但底座（持仓、数据接入、MCP Server、调度器）共用，新增模块属于横向扩展而非重写

## 2026-05-15 第四轮决策（重大方向调整：AI 角色降级与产品定位转向）

### 背景

用户在审阅 v0.2 产品定位文档后,提出两个关键质疑:

1. **担心 1**:当前产品定位中大模型占比过大,但现实可用的靠谱大模型不多。
   不靠谱的 AI 给出幻觉或不正确的结果,可能弊大于利。
2. **担心 2**:从用户个人角度,真正想要的是一个"**能规范我的执行、记录我的执行、根据执行结果(实际收益)来迭代我的投资策略**"的产品,而不是"AI 替我做深度分析"的产品。

PM 评估后判断:**用户的两个担心都成立,且应该比用户原本担心的更强**。

#### 关键评估结论

| 维度 | 评估结果 |
|---|---|
| AI 在金融领域的可靠性 | 低且难以即时验证 |
| AI 幻觉的伪装度 | 极高(编出的研报数据格式完美,普通人难辨) |
| 金融决策的容错率 | 极低(错一个判断可能损失几万到几十万) |
| AI 错误的反馈周期 | 极长(3 个月到 3 年才能验证对错) |
| v0.2 定位的内在矛盾 | "AI-Native + 数据轻推理重 + 巡检自动化"本质上是把产品命脉绑定在 baseline-05 中用户自己说"不能完全信任"的东西上 |
| 用户的真实痛点本质 | 不是"AI 不够强",而是"自己执行不规范 + 复盘不彻底 + 经验沉淀不系统" |

#### 用户提出的新角度

> "我更想要的,应该是一个能规范我的执行、记录我的执行,然后根据执行结果(实际收益)来迭代我的投资策略,这样一个产品。"

PM 判断:**这个方向是正确的,且需要做三个升级**:
1. 不是"放弃 AI",而是"把 AI 严格降级为数据秘书 + 复盘陪练"
2. 把"个人化数据"作为真正的产品壁垒(通用 AI 不知道你的历史,你的执行日志独一无二)
3. 严格区分"决策时刻 / 持有时刻 / 复盘时刻",不同状态用不同产品形态

### 决策

| 编号 | 问题 | 决策 |
|---|---|---|
| Q13 | 产品大方向 | **中间路线 B+**:主体转向"流程+记录+复盘",AI 严格降级为数据秘书。AI 仍可在巡检中**填四象限的事实部分**,但**分类与结论由用户做**。 |
| Q14 | MVP 范围 | **四模块全要**:决策日志 + Checklist + 复盘助手 + 规则化监控。合并后实际为 6 模块(显式独立"持仓状态机"和"热点信息汇总")。 |
| Q15 | 热点扫描的去留 | **保留但严格降级**:AI 不下结论,只做信息汇总(热点新闻原文 + 相关标的清单),关联与判断由用户做。 |

### 关键架构判断

> 这是项目启动以来**最大的方向性调整**,需要明确记录:

1. **产品骨架置换**:
   - v0.2: AI-Native(AI 是产品的核心)
   - v0.3: **流程 + 记录 + 复盘是产品骨架,AI 是辅助层(可拔插)**

2. **AI 的硬约束(架构级)**:
   - AI **永远不写**结论性字段(分类、行动建议、置信度等)
   - AI **只写**事实性字段(数据、原文、汇总)
   - schema 层强制 `author: user` 校验,系统拒绝 AI 直接写入结论
   - 架构预留"AI 完全关闭"的开关:AI 全部不可用时,产品依然能用 CLI 完成核心工作流

3. **MVP 模块结构**:
   ```
   M1 持仓状态机(底座) → M2 Checklist + M3 Journal + M4 监控 → M5 复盘 → M6 热点汇总
   ```

4. **三种投资活动状态的产品形态分离**:
   - 决策时刻(低频高风险): 强制 Checklist + AI 辅助数据 + 写 Journal
   - 持有时刻(高频低风险): 规则化监控,几乎不需要 AI
   - 复盘时刻(周期性): 历史数据汇总 + 错误模式扫描,AI 不下结论

### 替代方案与放弃理由

#### 替代方案 1: 保留 v0.2 但加强约束

> 让 AI 仍做四象限判断,但强制带置信度 + 反转条件 + 数据出处。

**放弃理由**:
- 这只是"礼仪性约束",AI 仍然在下结论
- 用户无法即时验证 AI 给的"置信度"是否合理
- AI 会学会用规范格式包装幻觉,反而更难识别

#### 替代方案 2: 完全放弃 AI

> 做一个纯本地的 Checklist + Journal 系统,完全不接 AI。

**放弃理由**:
- 矫枉过正,AI 在"数据汇总"和"信息检索"上确实有价值
- 用户已经在订阅 Cursor/Claude,边际成本极低
- 关键是"如何让 AI 出错时损失最小",而不是"完全不用 AI"

#### 替代方案 3: 等更靠谱的 AI 出现再做

> 推迟项目,等 3-5 年后 AI 更可靠。

**放弃理由**:
- 用户的执行规范化痛点是**当下**的痛点,等不起
- "流程 + 记录 + 复盘"产品的价值不依赖 AI,现在就能落地
- Journal 越早开始记越好(历史价值会随时间复利)

### 后续维护规则

- 任何新功能讨论必须先经过"AI 必须不写结论"的硬约束筛查
- baseline-05 的所有"四大严格边界"在 v0.3 中升级为**架构级硬约束**,不再仅是协作礼仪
- 阶段 2 文档撰写时,每个场景都必须明确标注"AI 的允许动作 / AI 的禁止动作"

## 2026-05-15 第五轮决策(结构性增补: L1 研究素材库 + 风险护栏 M7 + MVP 拆二期)

### 背景

用户在审阅 v0.3 产品定位文档后,提出三个新议题:

1. **热点的定位疑问**: 热点是核心功能项还是补充项? 用户指出"不做操盘手不应频繁选股"与"健壮组合应有短线配置"两者矛盾。
2. **价格评估缺位**: 买卖最终落到价格,是否需要独立的价格评估模块?
3. **专业角度的开放扫描**: 从投资专业角度,产品定位还有什么遗漏或方向不对的点?

PM 系统化扫描后,发现 v0.3 还存在以下结构性空白:
- **热点的三种意义被混淆**(短线机会 / 市场状态指示器 / 反向警示信号), v0.3 只覆盖了第一种
- **风险管理几乎完全缺失**(仓位、集中度、回撤、机会成本、个人禁区都没有)
- **选股环节被相对弱化**(用户称"慎重决策"但产品里没有承载流程)
- **决策心理纪律没有产品化**(情绪标签轻量但价值高)
- **信息源可信度无分级 + 数据快照可被覆盖**(数据架构隐患)
- **AI 自动入库 vs 手动录入的"知识资产化"完全缺失**(用户在第二轮提问中主动补充)

#### 用户第二轮主动补充的关键洞察

> "很多资讯它的迭代周期是比较久的,例如监管披露、业绩数据、流水数据、重大新闻等。所以咱们的数据仓库,应该是个动态补充的池,它不需要每次都去重复爬取数据,然后也可以支持录入一些数据,例如一些爬不到的资讯和个人认为比较有意义的文章分析,甚至可以是某个关注的比较大牛的人的动态。"

PM 判断: 这是**数据架构层面的核心理念问题**(定位级,非实现级),需要正式作为一个独立的"数据基础设施层"(L1 研究素材库)进入产品定位,与业务模块并列。这是 v0.3 最大的结构性空白。

### 决策

| 编号 | 议题 | 决策 |
|---|---|---|
| Q1 | 热点重定位 | **拆分**: M4 监控吸收"市场状态画像 + 板块异动告警"(给主仓), M6 重命名为"候选池"(给副仓,事件驱动,周/月级,不做日级炒题材) |
| Q2 | 价格/估值评估 | **嵌入 M2**: 不独立成模块,在 Checklist 引擎里加"估值辅助子工具"(PE/PB 分位 + 同业对比 + PE 锚定测算),**只给数据不给结论** |
| Q3 | 风险护栏 M7 | **新增 M7,拆二期**: MVP-1 做仓位规则 + 个人禁区, MVP-2 做机会成本跟踪 + 回撤告警 + 集中度管理 |
| Q4 | 观察池 + 情绪标签 | **都加**: M1 状态机明确独立 `watching` 子状态(轻量 Checklist + 月度评估 + 升级/剔除路径); Checklist 加 `emotion_tag` 枚举字段(冷静/焦虑/兴奋/恐惧/贪婪/FOMO) |
| Q5 | L1 研究素材库 | **独立为数据基础设施层**: 与业务模块并列,自动入库 + 手动录入 + 元数据标准(source/tier/timestamp/related_stocks/tags/author) + 检索;支持调研纪要、付费研报、雪球深度帖、关注大牛观点、个人笔记的录入 |
| Q6 | 数据架构原则 | **两项都写入 01 作为架构级硬约束**: (a) 信息源分级 S/A/B/C/D, 所有数据必须带 source + tier + timestamp;(b) 决策快照"冻结即不变",L1 原始数据可版本化追加,但 Journal 中的 data_snapshot 只读 |
| Q7 | MVP 拆期 | **拆二期**: MVP-1(13-17 周,决策完整闭环) + MVP-2(12-16 周,增强能力) |

### 关键架构判断

> v0.4 不是对 v0.3 的推翻,而是**在 v0.3 骨架上做三处加强**: 数据资产化 / 风险管理 / 流程完整性。

#### 新的产品架构(v0.4)

```
【数据基础设施层】
└── L1 研究素材库(自动入库 + 手动录入 + 元数据 + 检索)
        ↑ 供给所有业务模块

【业务模块层】(7 个)
├── M1 持仓状态机(含 watching 观察池子状态)
├── M2 Checklist 引擎(含估值辅助子工具 + emotion_tag)
├── M3 决策日志 Journal(含 L1 引用 + 快照冻结)
├── M4 规则化监控(含市场状态画像 + 板块异动)
├── M5 复盘助手(含策略画像 + emotion/tier 相关性)
├── M6 候选池(原 v0.3 M6 重命名,弱化日级)
└── M7 风险护栏(仓位规则 + 个人禁区 [+MVP-2 机会成本/回撤/集中度])

【AI 辅助层】 通过 MCP 暴露,只取数据/检索/汇总,永不写结论
```

#### 新增的架构级硬约束

1. **信息源可信度分级**(S/A/B/C/D): 所有数据带 tier 标签, C/D 级作为主要依据时系统弹确认
2. **决策快照冻结**: Journal 的 data_snapshot 一旦写入只读, L1 后续版本更新不回填覆盖
3. **数据流向单向**: Python 取数 → 调 Go 端 L1 服务接口写入 → 业务模块按需读 L1 → 用户审阅 → 用户填结论 → 写 Journal
4. **风险护栏作为决策拦截层**: 触发规则/禁区时, Checklist 提交会被拦截, 强制写"例外说明", 记入 Journal 永久保存

### 替代方案与放弃理由

#### 替代方案 1: 不引入 L1, 用 Notion / 文件夹自己管理研究素材

**放弃理由**:
- 无法跟决策 Journal 双向链接,复盘时无法关联"当时看了什么"
- 缺少元数据标准(tier 分级、关联标的、标签),长期会变成乱仓
- 用户已明确提出"应该是个动态补充的池"的需求

#### 替代方案 2: 风险护栏只做警告不做拦截

**放弃理由**:
- 投资中"事中拦截"远比"事后告警"有效
- baseline-05 用户已说"对单产品依赖型公司主动控制",这就是事中拦截的需求
- 拦截+例外说明的机制反而培养纪律性,例外说明本身就是复盘的素材

#### 替代方案 3: 把估值评估做成独立模块 M8

**放弃理由**:
- 估值数据的使用场景**只有**填 target_price 那一刻,独立成模块过度设计
- 嵌入 M2 后与 Checklist 工作流无缝衔接
- 工期可省 1-2 周

#### 替代方案 4: MVP 一次性做完不拆期

**放弃理由**:
- 总工期 25-33 周,一次性 6-8 个月没有阶段性成果,心理压力大
- MVP-1 完成时核心闭环已经能跑,价值已开始产出
- MVP-2 可根据 MVP-1 使用反馈调整优先级

#### 替代方案 5: 把 v0.3 的 6 模块直接做完再加增量

**放弃理由**:
- L1 是其他模块的依赖,必须先做或并行做,不能等
- M7 风险护栏的"个人禁区"在 Checklist 提交时拦截,必须在 M2 同期上线
- watching 子状态是 M1 一部分,不能延后

## 2026-05-15 知识基线沉淀（关键里程碑）

### 背景
用户提出："这是个长期项目，会经常开新对话窗。需要把过去几天关于投资的深度对话沉淀到文档，避免上下文丢失。"

### 决策
在 `docs/_baseline/` 下创建 5 份"知识基线"文档，作为新对话的"必读上下文"：

1. **`01-投资理念与风格.md`**：用户的投资底层世界观（长线为主、ROE 思维、对散户优势的清醒认知）
2. **`02-当前持仓与个人逻辑.md`**：12 只持仓的"为什么买"卡片 + 目标价 + 止损位 + 风险红线
3. **`03-巡检方法论.md`**：四层模型（宏观/行业/公司/市场）+ 四象限分类 + 四维度判断
4. **`04-历次巡检结论基线.md`**：5/12 三批巡检的结论钉桩，作为后续对比基线
5. **`05-认知陷阱与AI协作边界.md`**：用户已识别的四大致命误区 + AI 协作的四条硬性边界

同时重写 `README.md`，在最显眼位置加入 **"🤖 新对话开始时必读（AI Onboarding）"** 章节，明确加载顺序。

### 影响
- 任何新对话的 AI 在 5 分钟内能完整加载用户的投资上下文
- 不再依赖"对话历史记忆"，所有重要判断都在文档里
- 用户可以放心切换 workspace 到 `investment-assistant/` 并开新对话窗
- 后续所有功能开发都必须以这 5 份基线为输入

### 替代方案与放弃理由
- **替代方案 1**：直接把所有对话拼成一份长文档 → 放弃，因为对话里有大量过程性内容（探讨、修正、对比），不利于 AI 快速加载
- **替代方案 2**：只做一份"投资知识库"汇总 → 放弃，因为不同维度（理念 / 持仓 / 方法 / 结论 / 陷阱）的更新频率不同，分文件更利于维护

### 后续维护规则
- **基线 02（持仓）**：季报后必更新；关键事件（异环新卡池、智谱大涨等）即时更新
- **基线 03（方法论）**：当用户的巡检逻辑发生进化时更新
- **基线 04（结论）**：每次新巡检完成后追加新批次（保留历史，不覆盖）
- **基线 05（边界）**：当 AI 协作出现新的"反向修正"时更新
