## 2026-05-15 项目启动

### 起源
基于此前数次关于个人投资逻辑巡检的深度对话，决定将"投资分析"系统化为一个长期演进的产品。

### 第一轮决策（产品基础形态）

| 编号 | 问题 | 选项 | 决策 |
|---|---|---|---|
| Q1 | 用户范围 | 仅自己 / 自己+亲友 / SaaS / 开源 | **仅自己用** |
| Q2 | 部署形态 | CLI / 本地Web / 云Web / App / 多前端 | **后端 + 多前端**（CLI/Web/App，后端 API 统一） |
| Q3 | AI 角色 | 汇总 / 深度分析 / 信号 / 自动执行 | **深度分析协作者**（联网、判逻辑、给场景测算） |
| Q4 | MVP 范围 | 巡检 / 选股 / 买点 / 卖点 / 待定 | **待 PM 给推荐后确认** |

### 第二轮决策（数据、AI、协作）

| 编号 | 问题 | 选项 | 决策 |
|---|---|---|---|
| Q5 | 数据策略 | 免费 / 低付费 / 中付费 / 混合 | **混合**：免费结构化数据 + AI/Web Search 抓实时叙事 |
| Q6 | 投资周期 | 长线 / 长+波段 / 波段 / 全周期 | **长线为主 + 部分仓位做热点轮动** |
| Q7 | AI 接入方式 | API Key / 本地LLM / Cursor代理 / 多模型 | **复用 Cursor / Claude Desktop（MCP 协议）** |
| Q8 | 交互模式 | 对话 / 仪表盘 / 报告 / 混合 | **混合**：仪表盘 + 对话 + 主动推送 |

### 关键架构判断（基于 Q7）

> 因为选了 Cursor MCP 而不是自带 API Key，**产品本质是"给 LLM 用的工具集"，而不是"套了 LLM 的应用"**。
>
> 这意味着：
> 1. 后端不直接调用 LLM API，节省 token 成本
> 2. 后端实现为 MCP Server，把"取财报""算估值""跑巡检""读持仓"等能力暴露为 MCP Tools
> 3. AI 在 Cursor / Claude Desktop 里调用这些工具完成深度分析
> 4. Web UI 提供仪表盘视图，CLI 提供脚本化入口，App 提供推送通知

### 第三轮决策（MVP 范围、技术栈基线）

| 编号 | 问题 | 决策 |
|---|---|---|
| Q9 | MVP 范围 | **「持仓管理 + 逻辑巡检 + 热点扫描」**（长短双引擎，比 PM 原推荐多一个热点扫描模块） |
| Q10 | 编程语言 | **混合：Python 做数据采集/分析，Go 做后端 API + MCP Server** |
| Q11 | 持仓数据来源 | **手动维护 YAML/CSV 文件** |
| Q12 | 阶段 1 收尾方式 | 用户先审阅 v0.1 定位文档 → 反馈后再进入阶段 2 |

### 关键架构判断（基于 Q10）

> 选用 Python + Go 混合，意味着系统会有**两个进程层**：
>
> 1. **Python 数据/分析层**（`data-worker`）：调用 AKShare/Tushare、爬虫、跑财务计算、与 Web Search 协作
> 2. **Go 后端层**（`core-server`）：暴露 RESTful/gRPC API + MCP Server + 调度器 + 持仓状态管理
>
> 二者通过 **本地 RPC**（gRPC 或 HTTP）通信。Python 不直接对外暴露端口，所有外部入口（CLI/Web/MCP）走 Go。
>
> **优点**：Python 拿 pandas/AKShare 生态红利，Go 拿强类型/稳定性红利；分工清晰
> **代价**：双语言项目，需要管两个依赖系统（Poetry/uv + Go modules），需要进程间通信契约

### 关键范围调整（基于 Q9）

> 原 PM 推荐 MVP = 「持仓管理 + 巡检」（纯长线）
> 用户要求 MVP = 「持仓管理 + 巡检 + 热点扫描」（长短双引擎）
>
> **影响**：
> - 数据采集层需要新增"热点话题/题材"采集器（如东财涨停板、雪球热度榜、淘股吧/股吧热帖）
> - AI 工具集需要新增"热点 → 受益标的关联""短线弹性评估"工具
> - MVP 工期会从原计划的 4-6 周扩展到 6-8 周
> - 但底座（持仓、数据接入、MCP Server、调度器）共用，新增模块属于横向扩展而非重写

## 2026-05-15 知识基线沉淀（关键里程碑）

### 背景
用户提出："这是个长期项目，会经常开新对话窗。需要把过去几天关于投资的深度对话沉淀到文档，避免上下文丢失。"

### 决策
在 `docs/_baseline/` 下创建 5 份"知识基线"文档，作为新对话的"必读上下文"：

1. **`01-投资理念与风格.md`**：用户的投资底层世界观（长线为主、ROE 思维、对散户优势的清醒认知）
2. **`02-当前持仓与个人逻辑.md`**：12 只持仓的"为什么买"卡片 + 目标价 + 止损位 + 风险红线
3. **`03-巡检方法论.md`**：四层模型（宏观/行业/公司/市场）+ 四象限分类 + 四维度判断
4. **`04-历次巡检结论基线.md`**：5/12 三批巡检的结论钉桩，作为后续对比基线
5. **`05-认知陷阱与AI协作边界.md`**：用户已识别的四大致命误区 + AI 协作的四条硬性边界

同时重写 `README.md`，在最显眼位置加入 **"🤖 新对话开始时必读（AI Onboarding）"** 章节，明确加载顺序。

### 影响
- 任何新对话的 AI 在 5 分钟内能完整加载用户的投资上下文
- 不再依赖"对话历史记忆"，所有重要判断都在文档里
- 用户可以放心切换 workspace 到 `investment-assistant/` 并开新对话窗
- 后续所有功能开发都必须以这 5 份基线为输入

### 替代方案与放弃理由
- **替代方案 1**：直接把所有对话拼成一份长文档 → 放弃，因为对话里有大量过程性内容（探讨、修正、对比），不利于 AI 快速加载
- **替代方案 2**：只做一份"投资知识库"汇总 → 放弃，因为不同维度（理念 / 持仓 / 方法 / 结论 / 陷阱）的更新频率不同，分文件更利于维护

### 后续维护规则
- **基线 02（持仓）**：季报后必更新；关键事件（异环新卡池、智谱大涨等）即时更新
- **基线 03（方法论）**：当用户的巡检逻辑发生进化时更新
- **基线 04（结论）**：每次新巡检完成后追加新批次（保留历史，不覆盖）
- **基线 05（边界）**：当 AI 协作出现新的"反向修正"时更新
