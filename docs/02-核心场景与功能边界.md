## 一、本阶段目标

阶段 1 已经回答“这个产品是什么、为什么做、原则是什么”。

阶段 2 要回答更具体的问题：

1. 用户在什么场景下使用它？
2. 每个场景的输入、流程、输出是什么？
3. 哪些功能必须做，哪些明确不做？
4. 哪些判断由用户完成，哪些事实整理可由系统或 AI 辅助？
5. MVP-1 与 MVP-2 的边界如何拆，避免第一期范围膨胀？

本文档不是技术架构设计，不讨论具体数据库表、接口协议、数据源实现；这些放到阶段 3 / 阶段 4。

**字段约定**：第五至十二章为场景速览；**Checklist 字段名、枚举值、校验规则以第十六章为准**。前文与第十六章不一致时，以第十六章为准。

## 二、阶段 2 的设计原则

### 1. 场景优先，不从模块出发

阶段 1 已经定义了 L1 + M1-M7 的模块全景，但阶段 2 不直接按模块写功能清单。

正确顺序是：

> 用户场景 -> 用户动作 -> 系统约束 -> 数据产物 -> 模块承载

否则容易把产品做成“模块拼盘”，而不是一套真实可用的投资工作流。

### 2. 所有高风险场景都必须有强制留痕

以下动作必须写入 Journal 或相关历史记录：

- 加入观察池
- 建仓
- 加仓 / 减仓
- 巡检结论变更
- 卖出
- 风险护栏例外
- 叙事阶段判断
- 复盘后修改个人规则

只要会影响未来收益归因，就不能只存在于脑子里或临时对话里。

### 3. AI 只处理事实，不进入结论字段

每个场景都必须明确：

- AI 允许动作
- AI 禁止动作
- 用户必须填写的字段

核心约束沿用阶段 1：

> AI 是数据秘书与复盘陪练，不是决策者。任何分类、行动建议、置信度、叙事阶段、买卖判断，都必须由用户填写。

### 4. MVP-1 只跑通闭环，MVP-2 再增强智能性

MVP-1 的成功标准不是“分析能力很强”，而是：

> 一笔投资从研究、观察、建仓、持有、巡检、卖出到复盘，能完整记录、可追溯、可复用。

叙事信号包、错过模式扫描、机会成本深度分析、Web UI 等增强能力放到 MVP-2。

## 三、核心用户状态

阶段 2 按四种用户状态组织场景。

| 状态 | 用户问题 | 产品目标 | 主要场景 |
|---|---|---|---|
| 冷启动 | 我已有实盘持仓，怎么导入系统而不破坏历史？ | 存量录入 + `legacy_over_limit` 标记 + 补录 thesis | S0.5 |
| 研究时刻 | 我看到了一份资料，它以后可能有用，怎么沉淀？ | 把研究素材资产化 | S0 |
| 决策时刻 | 我要不要把一个标的纳入观察、建仓、加仓、减仓或卖出？ | 强制 Checklist + 风险拦截 + Journal 留痕 | S1 / S1.5 / S2 / S2a / S4 / S5 / S7 |
| 持有时刻 | 我不想天天看盘，但关键变化不能漏 | 规则化监控，少打扰但不漏关键事件 | S3 |
| 复盘时刻 | 这段时间我到底哪里判断对了、哪里错了？ | 收益归因 + 错误模式沉淀 + 规则演进 | S6 |

## 四点五、决策快照（data_snapshot）约定

建仓、加仓、卖出、规则变更等高风险动作通过 Checklist 后，系统生成 `data_snapshot` 并写入 Journal。快照**一旦生成只读**，L1 后续更新不得回填覆盖（与 [01-产品定位与思路](01-产品定位与思路.md) 一致）。

MVP-1 快照最小内容：

| 字段组 | 内容 |
|---|---|
| `snapshot_at` | 决策时间 |
| `price_snapshot` | 标的现价、涨跌幅、距建仓/上次巡检变化 |
| `valuation_snapshot` | PE/PB/PS 分位、同业对比摘要（客观数据） |
| `market_snapshot` | 主要指数水位、板块涨跌、流动性指标摘要 |
| `library_refs` | 本次引用的 `library_item_id` 列表及当时 tier |
| `watchlist_context` | 若来自观察池：观察假设、待验证指标摘要 |
| `risk_context` | 触发/未触发的护栏规则、仓位占比 |

复盘时区分：`decision_snapshot`（当时看到的事实）与 `current_data`（复盘时新事实）。细节表结构见 [03-数据架构与数据源](03-数据架构与数据源.md)。

## 四点六、信息源 tier 与 Checklist 联动

凡引用 L1 素材或事实进入 Checklist / Journal：

1. 每条事实须带 `source` / `tier` / `timestamp`。
2. 若本次决策**主要依据**的素材最高 tier 为 **C 或 D**，提交前须完成 `tier_acknowledgement`（用户确认「知悉可信度较低」），并写入 Journal。
3. AI 可提示 tier，但**不得**替用户完成确认。

## 五、S0 研究素材入库

### 场景定义

用户看到一份可能对未来投资有价值的资料，或系统通过动态爬取发现一批可能与市场热点、叙事信号、持仓风险、观察池线索相关的信息，希望它们进入自己的长期研究素材库，而不是散落在浏览器收藏、微信、文件夹、临时爬虫结果或对话记录里。

因此 S0 不是一个纯“主动收藏”场景，而是两类入口并存：

| 入口 | 含义 | 目的 |
|---|---|---|
| 主动录入 | 用户主动保存 URL / 文件 / 文本 / 笔记 | 沉淀用户主观认为重要的材料 |
| 被动发现 | 系统定时爬取公告、新闻、研报热度、社区热帖、板块异动等信息 | 捕捉用户可能没看到的市场变化，再由用户决定是否入库、观察或忽略 |

典型素材：

- 公司公告、财报、业绩预告
- 研报、电话会纪要、调研纪要
- 雪球深度帖、公众号文章、行业媒体报道
- 用户自己的笔记
- 关注的大 V / 基金经理 / 行业专家观点
- 后续叙事信号包需要引用的历史案例材料

### 用户流程

1. 主动入口：用户通过 CLI 录入 URL / 文件 / 文本片段。
2. 被动入口：系统按规则爬取外部信息，生成候选素材队列。
3. 系统提取标题、时间、作者、来源、关联标的候选，并检索 L1 中相似素材，提示是否重复。
4. 用户确认是否入库、忽略、合并到已有素材，或转入观察池线索。
5. 系统要求填写或确认基础元数据。
6. 系统保存原文或文件快照。
7. 系统生成 `library_item_id`。
8. 后续 Checklist / Journal / 巡检 / 复盘 / 叙事信号包可引用该素材。

### 必填字段

| 字段 | 说明 |
|---|---|
| `title` | 素材标题 |
| `source` | 来源名称 |
| `tier` | S/A/B/C/D 信息源等级 |
| `timestamp` | 原始发布时间或录入时间 |
| `content_type` | announcement / report / article / note / transcript / data |
| `related_stocks` | 关联标的，可为空 |
| `tags` | 行业、主题、事件标签 |
| `summary_by_user` | 用户自己的简短备注，MVP-1 可选 |

### AI 允许动作

- 提取标题、发布时间、作者、关联标的候选。
- 对长文做事实摘要。
- 提醒可能的信息源等级。
- 检索 L1 中相似素材。
- 对被动爬取候选做去重、聚类和事实摘要。
- 标记“可能可转观察池”的线索，但不替用户决定。

### AI 禁止动作

- 判断这份材料是否“值得买”。
- 把社区观点包装成确定性事实。
- 用素材内容生成投资结论。
- 改写用户自己的 thesis。
- 把热点材料直接升级成观察池或建仓候选。

### MVP 边界

MVP-1：

- CLI 录入文本 / URL / 本地文件路径。
- **被动发现（简版）**：按持仓/观察池标的拉取公告、财报披露提醒等**结构化列表**；用户逐条确认入库或忽略（不做多源热点全自动爬虫）。
- 保存元数据（含 `source` / `tier` / `timestamp`）。
- 按标题、股票代码、标签**精确搜索**。
- 可被 Checklist / Journal 引用。

MVP-2：

- 多源爬取（新闻、研报热度、社区热帖）与候选聚类。
- 相似素材检索、去重增强。
- FTS5 全文检索。
- 简易 Web 录入界面。
- 自动抓取网页快照。
- 大 V / 专家动态的半自动入库。
- 与叙事信号包的历史案例检索联动。
- 更强的热点 / 叙事候选聚类。

## 五点五、S0.5 存量持仓初始化

### 场景定义

用户首次使用系统，需要把**已有实盘持仓**导入，而不是从零开始建仓。本场景解决冷启动：不强迫一次性补全全部历史 Journal，但须标记风险状态并留下可追溯起点。

### 用户流程

1. 用户通过 CLI 导入 `portfolio.yaml`（或 CSV 转 YAML）。
2. 系统校验代码、仓位、成本等基础字段。
3. 对每只标的：用户**补录简版 thesis**（可引用已有 L1 素材，或填 `no_library_reason`）。
4. 系统运行 M7：若超过仓位/集中度阈值，标记 `legacy_over_limit`，**允许录入、不阻断**。
5. 为每只标的生成 `import_journal`（`action_type: import`）及初始 `lot`（若有多批次可拆多个 lot）。
6. 标的状态直接设为 `holding`（跳过 `watching`）。
7. 提示用户：后续变更须走正式 Checklist（建仓/加仓/卖出），不可再静默改 YAML。

### 必填字段（简版）

| 字段 | 说明 |
|---|---|
| `code` / `name` | 标的 |
| `position_pct` | 当前占总资产比例 |
| `cost_basis` | 成本价或成本区间 |
| `position_type` | core / swing |
| `import_thesis_summary` | 当前持有逻辑摘要 |
| `related_library_ids` 或 `no_library_reason` | 依据素材 |
| `legacy_flags` | 系统生成的超限标记列表 |

### MVP 边界

MVP-1：支持导入 + `legacy_over_limit` + `import_journal` + 初始 lot。  
MVP-2：导入时可选关联历史外部交易记录（若有）。

## 六、S1 选股与观察池

### 场景定义

用户暂时不想买，但认为某个标的或主题值得跟踪，希望进入观察池，后续定期评估是否升级为建仓候选或剔除。

观察池不是“想买清单”，而是“需要持续验证的假设清单”。

### 用户流程

1. 用户新增观察标的。
2. 填写轻量观察 Checklist。
3. 关联已有 L1 素材。
4. 设定后续观察指标和复查时间。
5. 系统写入 `watchlist.yaml` 或对应状态记录。
6. 月度评估时提示保留、升级、剔除。

### 必填字段

| 字段 | 说明 |
|---|---|
| `code` / `name` | 标的 |
| `watch_reason` | 为什么值得观察 |
| `hypothesis` | 待验证假设 |
| `key_metrics_to_watch` | 后续要看的指标 |
| `expected_trigger` | 什么发生后考虑建仓 |
| `invalid_condition` | 什么发生后移出观察池 |
| `review_date` | 下次复查时间 |
| `related_library_ids` | 引用素材 |

### AI 允许动作

- 帮用户整理标的基础信息。
- 根据用户输入拆出待验证指标候选。
- 检索 L1 中已有相关资料。
- 汇总近期公告、财报、新闻原文。

### AI 禁止动作

- 判断“应该加入观察池”。
- 判断“应该建仓”。
- 给标的排序。
- 给上涨空间或买点建议。

### MVP 边界

MVP-1：

- `watching` 状态。
- 轻量观察 Checklist。
- 月度复查提醒。
- 支持从观察池升级到建仓 Checklist。

MVP-2：

- 观察池批量复查报告。
- 与市场状态画像、叙事信号包联动。
- 观察池机会成本统计。

## 六点五、S1.5 候选池（M6）

### 场景定义

**M6 候选池**与 S0「被动发现」、S1「观察池」分工不同：

| 维度 | S0 被动发现 | S1.5 候选池（M6） | S1 观察池 |
|---|---|---|---|
| 频率 | 可按日拉列表 | **周 / 月级**事件扫描 | 用户主动 + 月度复查 |
| 产物 | `library_item` 或线索 | **候选标的 / 主题清单** | `watchlist_item` + 假设 |
| AI 角色 | 摘要、去重 | **只汇总不下结论** | 整理字段，不判断买卖 |
| 用户动作 | 入库 / 忽略 | 决定是否进入 **S1 观察池 Checklist** | 保留 / 升级建仓 / 剔除 |

典型输入：政策事件、行业景气拐点、板块资金异动（周级）、财报季行业对比等。  
**不做**日级「今天买什么」、涨停板推荐、龙头弹性排序。

### 用户流程

1. 系统按周 / 月或事件触发，生成 `candidate_report`（Markdown + 元数据）。
2. 报告包含：事件摘要、相关标的列表、每条事实的 source/tier/timestamp。
3. 用户对每条候选：忽略 / 关联 L1 入库 / **发起 S1 观察池 Checklist**。
4. 进入观察池后走 S1 流程，不再保留在候选池活跃列表。

### MVP 边界

MVP-1（简版）：

- CLI 手动维护 `candidates.yaml`（事件 + 标的列表 + 备注）。
- 支持从候选一键发起观察池 Checklist。
- 不做自动多源扫描。

MVP-2：

- 事件驱动自动扫描（与 M4 市场状态、板块异动联动）。
- 候选报告定期推送。
- 与叙事信号包、错过模式扫描交叉引用。

### AI 允许 / 禁止

- **允许**：汇总新闻/公告原文、列标的、检索 L1、格式化报告。
- **禁止**：推荐买入、排序弹性、判断「龙头」、生成完整投资建议。

## 七、S2 建仓决策

### 场景定义

用户准备买入一只标的。系统必须强制用户完成建仓 Checklist，检查风险护栏，并把决策当时的上下文冻结到 Journal。

建仓是产品中最重要的高风险场景。

### 用户流程

1. 用户发起建仓。
2. 系统加载标的当前状态、观察记录、L1 素材、估值辅助数据。
3. 用户填写建仓 Checklist。
4. 系统执行风险护栏检查。
5. 若触发风险规则，用户必须写例外说明。
6. 若存在未过期叙事信号包，MVP-2 要求先完成 `narrative_stage_assessment`。
7. Checklist 通过后生成 Journal 与 `data_snapshot`（见 4.5 节），并创建初始 `lot`。
8. 标的状态变为 `holding`。

### 必填字段

> 完整字段、枚举与校验见 **16.2 建仓 Checklist**。下表为场景速览。

| 字段 | 说明 |
|---|---|
| `action_type` | buy |
| `buy_reason_summary` | 一句话买入理由 |
| `investment_thesis` | 完整买入逻辑 |
| `position_type` | core / swing |
| `expected_return_driver` | 预期收益来源（至少 1 项） |
| `target_price` | 目标价或区间，用户填 |
| `stop_loss` | 止损/减仓线或区间，用户填 |
| `reversal_conditions` | 逻辑反转条件（至少 1 项） |
| `position_size_plan` | 含 `initial_pct`、`max_pct` |
| `opportunity_cost_benchmark` | HS300 / CSI_TECH / sector_index / custom |
| `confidence` | low / medium / high |
| `identified_risks` | 至少 1 项 |
| `emotion_tag` | calm / anxious / excited / fearful / greedy / fomo |
| `related_library_ids` 或 `no_library_reason` | 素材引用 |
| `risk_guardrail_result` | 风险护栏结果 |
| `narrative_stage_assessment_id` | MVP-2：有未过期信号包时必填 |

### AI 允许动作

- 拉取财务、估值、公告、新闻等事实。
- 汇总 L1 中的历史材料。
- 帮用户把已写内容格式化。
- 提醒 Checklist 漏填项。
- 呈现历史相似决策的结果。

### AI 禁止动作

- 写 `investment_thesis` 的结论版本。
- 写 `target_price` / `stop_loss`。
- 写 `confidence`。
- 判断“可以买”。
- 绕过风险护栏。
- 在叙事场景写 `narrative_stage`。

### MVP 边界

MVP-1：

- 建仓 Checklist。
- Journal 冻结快照。
- L1 引用。
- 基础估值辅助数据。
- M7 基础风险护栏：单标的仓位、单板块集中度、个人禁区。

MVP-2：

- 机会成本预警。
- 回撤和集中度增强。
- 未过期叙事信号包强拦截。
- 历史相似决策回看。

## 七点五、S2a 加仓决策

加仓是独立高风险场景，**不复用建仓 Checklist**。流程、字段、反报复性加仓规则见 **16.4 加仓 Checklist**。

场景要点：

1. 触发来源：S4 巡检 `planned_action = add`、价格回调、thesis 增强、MVP-2 叙事信号包、手动。
2. 须重新跑 M7；生成加仓 Journal、新 `lot`；与原建仓 lot **分开归因**。
3. MVP-2：标的有未过期叙事信号包时，须先完成 `narrative_stage_assessment` 并关联 `narrative_stage_assessment_id`（与建仓一致）。

## 八、S3 日常监控

### 场景定义

用户不想高频看盘，但希望系统捕捉会影响 thesis 的关键变化。

日常监控的目标是“少打扰，但不能漏掉关键事件”，不是制造短线交易冲动。

### 监控对象

MVP-1：

- 持仓标的公告。
- 财报披露日历。
- 价格触及用户设定阈值。
- 估值分位触及极端区间。
- 用户自定义指标。

MVP-2：

- 市场状态画像。
- 板块异动。
- 机会成本变化。
- 叙事六维信号。
- 海外同业预演。

### 输出类型

| 类型 | 说明 |
|---|---|
| `info` | 信息更新，不要求动作 |
| `watch` | 值得关注，下次巡检看 |
| `action_required` | 触发 Checklist 或巡检 |
| `risk` | 触发风险护栏或红线 |

### 监控事件 → 推荐流程（系统只提醒，用户发起）

| 事件类型 | 推荐流程 | 说明 |
|---|---|---|
| 公告 / 财报披露 | S4 巡检 或 S0 入库 | 事实进 L1，是否改 thesis 由用户判断 |
| 价格达 `target_price` | S5 卖出 或 S4 再分析 | 不自动卖出 |
| 价格破 `stop_loss` | S4 巡检 或 S5 卖出 | 须用户确认是否逻辑破坏 |
| `reversal_conditions` 命中 | **S4 巡检（优先）** | 强提醒，建议完成巡检 Checklist |
| 风险护栏 `risk` | S5 减仓 或 M7 例外 | 可能需降低暴露 |
| 候选池 / 被动线索 | S1 观察池 或 S0 入库 | 见 S1.5 / S0 |
| MVP-2 叙事信号 | S7 阶段判断 → S1/S2/S2a/S4 | 不下买卖结论 |

### AI 允许动作

- 汇总公告原文。
- 提取财报关键数据。
- 对比上一次监控记录。
- 把事件整理成 Markdown。

### AI 禁止动作

- 把监控事件解释成买卖建议。
- 对板块异动给“龙头推荐”。
- 把日级热点包装成机会。
- 用叙事语言替代客观信号。

### MVP 边界

MVP-1：

- 个股层监控。
- 规则触发事件记录。
- Markdown / CLI 输出。

MVP-2：

- 市场状态画像。
- 板块异动告警。
- 叙事信号包生成。
- 邮件或微信推送。

## 九、S4 持仓巡检

### 场景定义

用户定期或事件触发地检查某只持仓的原始 thesis 是否仍然成立，是否需要升级、降级、加仓、减仓或继续观察。

巡检不是 AI 自动给结论，而是系统把事实和历史上下文准备好，用户完成判断。

### 用户流程

1. 用户手动触发或系统定时触发巡检。
2. 系统加载上次 thesis、历史 Journal、L1 素材、最新事实数据。
3. 系统按巡检模型填充**事实部分**（见下「五层与 MVP 分层」）。
4. 用户填写四维度判断。
5. 用户选择四象限分类。
6. 用户填写行动计划、置信度、反转条件。
7. 系统生成巡检记录，并与持仓、Journal 关联。

### 五层巡检模型与 MVP 分层

| 层级 | 内容 | MVP-1 | MVP-2 |
|---|---|---|---|
| 第 1 层 宏观流动性 | 成交额、两融、北向等事实 | 事实摘要（可简） | 完整自动填充 |
| 第 2 层 行业逻辑 | 行业 ROE、景气指标 | 事实摘要 | 完整自动填充 |
| 第 3 层 公司基本面 | 财报、公告、估值 | 事实摘要 | 完整自动填充 |
| 第 4 层 市场行为 | 股价、成交、相对收益 | 事实摘要 | 完整自动填充 |
| 第 5 层 叙事周期 | 六维信号矩阵 + 阶段判断 | **不自动填** | 关联 S7 信号包；有未过期包时须 `narrative_stage_assessment_id` |

说明：`core_narrative_status`（四维度之一）是用户对**买入 thesis / 核心故事**的判断，不等于第 5 层「市场叙事周期」信号包。详见 [baseline-03-巡检方法论](../_baseline/03-巡检方法论.md)。

### 必填字段

> 完整定义见 **16.3 持仓巡检 Checklist**。

| 字段 | 说明 |
|---|---|
| `industry_roe_trend` | improving / stable / deteriorating |
| `free_cash_flow_trend` | improving / stable / deteriorating |
| `market_share_trend` | gaining / stable / losing |
| `core_narrative_status` | intact / shifting / broken |
| `classification` | 四象限分类，用户填 |
| `planned_action` | hold / add / reduce / exit / keep_watching，用户填 |
| `confidence` | low / medium / high |
| `thesis_delta` | 与原 thesis 的差异 |
| `new_reversal_conditions` | 可选，更新反转条件 |

### AI 允许动作

- 填充第 1–4 层（MVP-1）及第 5 层客观信号（MVP-2，不含阶段结论）。
- 找出与上次巡检相比发生变化的数据。
- 检索相关 L1 素材。
- 把用户填写结果生成 Markdown 报告。

### AI 禁止动作

- 填四象限分类。
- 填计划动作。
- 填置信度。
- 判断“逻辑已破坏”。
- 用安慰性语言掩盖机会成本。

### MVP 边界

MVP-1：

- 手动触发巡检。
- 月度 / 季报后巡检提醒。
- 第 1–4 层事实区 + 四维度 + 四象限 Checklist。
- 巡检记录入库。

MVP-2：

- 第 5 层叙事信号与 `narrative_stage_assessment` 联动。
- 更完整的五层数据自动填充。
- 自动对比历史巡检。
- 巡检报告推送。

## 十、S5 卖出决策

### 场景定义

用户准备卖出或减仓。系统必须记录卖出原因、收益归因、是否符合原始 thesis、是否触发情绪或风险规则。

卖出不是交易结束，而是复盘数据的开始。

### 用户流程

1. 用户发起卖出 / 减仓。
2. 系统加载建仓 Journal、历次巡检、当前收益、目标价和反转条件。
3. 用户填写卖出 Checklist。
4. 系统检查是否违反个人禁区，例如恐慌止损、报复性交易。
5. 生成卖出 Journal。
6. 若全部卖出，状态变为 `closed`。

### 必填字段

> 完整定义见 **16.5 卖出/减仓 Checklist**。`sell_trigger` = 触发机制，`sell_reason` = 归因分类。

| 字段 | 说明 |
|---|---|
| `sell_type` | reduce / exit |
| `sell_trigger` | target_reached / stop_loss_reached / thesis_broken / … |
| `sell_reason` | logic_broken / target_achieved / valuation_too_high / risk_reduction / opportunity_switch / stop_loss / time_cost / other |
| `thesis_result` | validated / partially_validated / invalidated / not_enough_time |
| `return_result` | 绝对与相对收益（系统算） |
| `attribution` | 含 `result_category` 等（见 16.5） |
| `lesson` | 本次教训，必填 |
| `emotion_tag` | calm / anxious / excited / fearful / greedy / fomo / tired |
| `rule_change_suggestion` | 可选，是否建议改规则 |

### AI 允许动作

- 计算收益和相对收益。
- 汇总建仓以来的关键事件。
- 对照原始 thesis 和反转条件。
- 整理用户填写的教训。

### AI 禁止动作

- 判断“应该卖出”。
- 判断“卖早了 / 卖晚了”的结论。
- 写卖出原因。
- 用短期股价波动替代逻辑判断。

### MVP 边界

MVP-1：

- 卖出 Checklist。
- 关闭持仓状态。
- 自动关联原始建仓 Journal。
- 基础收益计算。

MVP-2：

- 机会成本归因。
- 情绪标签与收益相关性。
- 卖飞模式扫描。

## 十一、S6 周期性复盘

### 场景定义

用户在卖出时立即做单笔归因，并按月、季度、年度复盘投资行为，识别重复错误和有效策略，把经验沉淀为下一轮 Checklist / redlines / 风险规则。

复盘不是总结收益曲线，而是升级个人投资系统。归因也不是季度才发生，而是“卖出即归因、季度再汇总”的动态持续过程。

### 用户流程

1. 用户触发月度 / 季度 / 年度复盘。
2. 系统汇总期间交易、持仓变化、巡检记录、风险例外。
3. 系统生成事实部分和统计表。
4. 系统扫描错误模式候选。
5. 用户确认哪些是真问题。
6. 用户决定是否修改 Checklist、risk_rules、personal_redlines。
7. 系统生成复盘报告。

### 基础复盘维度

| 维度 | 说明 |
|---|---|
| 收益归因 | 已平仓收益、持仓浮盈亏、相对基准 |
| 行为归因 | 买入、加仓、减仓、卖出是否按规则执行 |
| Thesis 校验 | 原始判断被验证还是证伪 |
| 风险例外 | 触发规则后例外的实际结果 |
| 情绪标签 | 不同情绪下的决策质量 |
| 信息源质量 | 不同 tier 素材在决策中的表现 |
| 结果分类 | 区分流程错误、判断错误、执行错误、以及“当时没有错但结果不好” |

### AI 允许动作

- 汇总统计。
- 扫描候选错误模式。
- 找出历史相似交易。
- 把用户确认后的结论整理成报告。

### AI 禁止动作

- 替用户定义“你错在哪里”的最终结论。
- 自动修改 personal_redlines。
- 自动修改风险规则。
- 把短期亏损等同于错误。

### MVP 边界

MVP-1：

- 月度 / 季度基础复盘。
- 已平仓交易收益归因。
- 卖出时单笔归因。
- 季度归因汇总。
- Checklist 完成度统计。
- 风险例外统计。

MVP-2：

- 错误模式扫描。
- 策略画像。
- 叙事错过模式扫描。
- 信息源 tier 有效性统计。

## 十二、S7 叙事信号包与阶段判断

### 场景定义

系统发现某个板块或标的出现多维度异常信号，生成叙事信号包。用户查看信号包后，自行判断叙事处于什么阶段，并决定是否影响观察、建仓、巡检或复盘。

叙事信号包是反偏见工具，不是水晶球。

### 触发方式

MVP-2 支持三类触发：

1. 主动触发：用户手动生成某标的 / 板块信号包。
2. 月度触发：系统对观察池和持仓扫描。
3. 事件触发：出现财报超预期、海外同业大涨、研报数量异常、资金流异常等。

### 六维信号

| 维度 | 内容 |
|---|---|
| A 基本面 | 业绩超预期、收入结构、毛利拐点、订单、客户结构 |
| B 产业链 | 上游订单、CapEx、技术节点、海外同业预演 |
| C 资金面 | 公募、北向、ETF、龙虎榜、大宗、高管增减持 |
| D 关注度 | 研报数量、媒体提及、雪球热度、调研频率 |
| E 估值 | PE/PB/PS 分位、PEG、同业溢价折价 |
| F 价格行为 | 新高、放量、超额收益、突破形态 |

### 用户必填字段

| 字段 | 说明 |
|---|---|
| `narrative_stage` | sprout(萌芽) / validation(验证) / acceleration(加速) / markup(主升) / consensus(共识) / decline(衰退) |
| `reasoning` | 必须引用至少 3 个维度的信号 |
| `counter_signals` | 反向证据 |
| `reversal_conditions` | 阶段判断失效条件 |
| `decision_impact` | no_action / watch / inspect / prepare_buy_checklist |

### AI 允许动作

- 汇集六维客观信号。
- 引用原始来源。
- 检索 L1 中历史相似案例。
- 生成客观信号表格。

### AI 禁止动作

- 写 `narrative_stage`。
- 编造叙事故事链条。
- 判断“现在可以买”。
- 给涨幅空间。
- 把单维度异常包装成趋势。

### 强拦截规则

MVP-2 中：

- 若某标的存在**未过期**叙事信号包，**建仓（S2）与加仓（S2a）** Checklist 必须先完成 `narrative_stage_assessment` 并填写 `narrative_stage_assessment_id`。
- **深度巡检（S4）**：有未过期信号包时，须关联 `narrative_stage_assessment_id`，并与四象限结论对照（例：四象限仍「等风格切换」但叙事已「验证/加速」→ thesis 进化信号）。
- `narrative_stage_assessment` 必须由用户填写；须引用至少 3 个维度的信号作为理由。
- 信号包默认 **30 天**后失效（`expires_at`）；过期后不再强拦截建仓/加仓，历史评估仍保留供复盘。

### MVP 边界

MVP-1：

- 不做叙事信号包。
- 只在文档和 schema 中预留字段。

MVP-2A：

- 做叙事信号包。
- 做建仓强拦截。
- 做手动 `overseas_peers.yaml` 映射。
- 优先覆盖 AI 算力、游戏、券商三个板块。

MVP-2B：

- 做叙事错过模式扫描。
- 做历史相似案例算法增强。
- 做错过模式画像。

## 十二A、M1 持仓状态机

M1 不是静态持仓表，而是带流转规则的状态机（承载 S0.5 / S1 / S2 / S2a / S4 / S5）。

### 主状态（portfolio 标的）

| 状态 | 含义 | 典型进入 | 典型离开 |
|---|---|---|---|
| `unknown` | 系统未跟踪 | 首次见到代码 | → `watching` 或一次性导入 |
| `watching` | 观察池 | S1 Checklist | → `holding` / `removed` |
| `holding` | 持仓中 | S2 建仓 / S0.5 导入 | → `closed`（全部卖出） |
| `closed` | 已平仓 | S5 清仓 | 终态；可新建 `watching` |

### 观察池剔除

| 状态 | 含义 |
|---|---|
| `removed` | 观察项剔除（假设证伪或不再跟踪），**不是** `closed` |

### 任务态（不占主状态，用任务/Checklist 表达）

| 任务态 | 含义 | MVP-1 |
|---|---|---|
| `inspecting` | 巡检进行中 | 用 `inspection_record` + 提醒表达，不强制改 YAML 主状态 |
| `adjusting` | 加仓/减仓 Checklist 进行中 | 用 Journal `action_type` 表达 |

> 与 [01-产品定位与思路](01-产品定位与思路.md) 中 `inspecting` / `adjusting` 主状态设计对齐：**MVP-1 采用「主状态精简 + 任务/流水表达」**，避免状态爆炸；若后续需要可在 MVP-2 将 `inspecting` 提升为主状态。

### 状态流转简图

```
unknown ──S1──► watching ──S2──► holding ──S5 exit──► closed
                  │                │
                  │                ├── S2a 加仓（仍 holding）
                  │                └── S4 巡检（仍 holding）
                  └── removed
S0.5 导入 ──────────────────────► holding（legacy 标记）
```

## 十三、跨场景功能边界

### 必做

| 功能 | 原因 |
|---|---|
| Checklist 强校验 | 防止高风险决策留白 |
| Journal 冻结快照 | 保证三年后可复盘当时上下文 |
| L1 素材引用 | 把研究资料变成长期资产 |
| 风险护栏拦截 | 把仓位和个人禁区变成事中约束 |
| 状态机 | M1：`watching` / `holding` / `closed` / `removed` + 任务态（见 12A） |
| tier 确认 | C/D 级主要依据须 `tier_acknowledgement`（见 4.6） |
| M6 候选池 | 周/月级事件候选 → 观察池，不下结论 |
| Markdown 报告 | 人类可读、Git 友好、便于复盘 |

### 明确不做

| 不做项 | 原因 |
|---|---|
| 自动下单 | 决策权必须在用户 |
| AI 自动生成结论报告 | 违反 AI 边界 |
| 日级短线热点推荐 | 会诱发频繁交易 |
| 机构级组合归因 | 超出个人 MVP 需要 |
| 社区、跟单、订阅 | 产品只服务用户本人 |
| 完整产业链图谱 | MVP 复杂度过高 |
| 实时行情终端 | 同花顺/雪球已足够 |

## 十四、MVP-1 范围建议

MVP-1 目标：跑通核心决策闭环。

建议包含：

1. **L1 简版**：主动录入；被动发现简版（持仓/观察池相关公告列表）；元数据；精确检索；Checklist 引用。
2. **S0.5 存量持仓导入**：`legacy_over_limit` + `import_journal` + 初始 lot。
3. **M1 状态机**：`watching` / `holding` / `closed` / `removed`（见 12A）。
4. **M2 Checklist（六类）**：观察池、建仓、**加仓**、巡检、卖出/减仓、周期性复盘（见第十六章）。MVP-2 起新增第七类 `swap`（换股，见 [docs/06 §D7](06-架构Review决议.md)）。
5. **M3 Journal**：不可篡改 + `data_snapshot` 冻结 + lot 跟踪。
6. **M4 个股层监控**：公告、财报日历、价格/估值阈值；`action_required` 路由（见 S3）。
7. **M5 基础复盘**：月度 + 季度；卖出单笔归因；**用户手动**确认 `confirmed_patterns`（不做自动错误模式扫描）。
8. **M6 候选池简版**：`candidates.yaml` 手动维护 + 一键进观察池。
9. **M7 基础风险护栏**：仓位规则 + 个人禁区（r001–r005 默认启用，r006–r012 预置默认关闭，见 18.6）。

建议不包含：

- Web UI。
- 叙事信号包（S7，仅 schema 预留）。
- 自动错误模式扫描 / 叙事错过模式扫描。
- FTS5 全文检索、多源全自动爬虫。
- 机会成本深度归因。
- 邮件/微信推送。

## 十六、MVP-1 Checklist 模板设计

本节开始把阶段 2 的讨论从“场景边界”推进到“用户实际要填什么”。

设计原则：

1. Checklist 是决策约束，不是写作文。
2. 必填字段只保留会影响未来复盘的内容。
3. AI 可以帮忙准备事实和格式化文本，但不能填写用户结论字段。
4. 每个 Checklist 都要能生成 Journal 或状态变更记录。
5. **本章为字段与枚举的权威定义**；第五至十二章场景节仅作速览。
6. 引用 L1 且主要依据 tier 为 C/D 时，须 `tier_acknowledgement`（见 4.6）。

### 16.1 观察池 Checklist

#### 场景定位

观察池是“待验证假设清单”，不是“想买清单”。

它承接两类入口：

1. 用户主动看到某个标的 / 主题，认为值得跟踪。
2. 系统通过 S0 被动发现热点、叙事、公告、研报热度或社区讨论后，提示用户“这可能值得观察”。

观察池 Checklist 的目标不是判断能不能买，而是把一个模糊兴趣点变成可跟踪、可证伪、可复查的假设。

#### 用户流程

1. 用户从主动录入、被动发现候选、或手动命令发起“加入观察池”。
2. 系统加载相关 L1 素材、近期事实、相似观察记录。
3. 用户填写观察池 Checklist。
4. 系统校验必填字段。
5. 生成 `watchlist_item`，标的进入 `watching` 状态。
6. 到达 `review_date` 后，系统提示用户复查：保留、升级建仓 Checklist、剔除、继续观察。

#### 字段分层

| 字段 | 类型 | 必填 | 填写者 | 说明 |
|---|---|---|---|---|
| `code` | string | 是 | 用户 / 系统候选 | 股票代码或主题代码；主题类可用自定义 id |
| `name` | string | 是 | 用户 / 系统候选 | 标的或主题名称 |
| `watch_type` | enum | 是 | 用户 | stock / sector / theme / person / event |
| `source_entry` | enum | 是 | 系统 | manual / passive_discovery / from_review / from_signal_pack |
| `watch_reason` | text | 是 | 用户 | 为什么值得观察 |
| `hypothesis` | text | 是 | 用户 | 需要验证的核心假设 |
| `key_metrics_to_watch` | list | 是 | 用户，AI 可建议 | 后续要看的指标，至少 1 项 |
| `expected_trigger` | text | 是 | 用户 | 什么发生后考虑进入建仓分析 |
| `invalid_condition` | text | 是 | 用户 | 什么发生后移出观察池 |
| `review_date` | date | 是 | 用户 / 系统默认 | 下次复查时间 |
| `priority` | enum | 是 | 用户 | low / medium / high |
| `related_library_ids` | list | 否 | 用户 / 系统候选 | 关联 L1 素材 |
| `related_positions` | list | 否 | 系统候选，用户确认 | 与现有持仓可能相关的标的 |
| `notes` | text | 否 | 用户 | 其他备注 |

#### 推荐默认值

| 字段 | 默认值 | 说明 |
|---|---|---|
| `review_date` | 30 天后 | 观察池不是永久收藏夹，默认一个月复查一次 |
| `priority` | medium | 用户可手动改 high / low |
| `source_entry` | 自动识别 | 主动录入为 manual，被动爬取为 passive_discovery |

#### 枚举定义

`watch_type`：

- `stock`：单一股票
- `sector`：行业 / 板块
- `theme`：主题 / 叙事，如 AI 算力、游戏出海
- `person`：关注的大 V / 基金经理 / 行业专家
- `event`：特定事件，如政策、产品发布、财报异常

`priority`：

- `low`：低频跟踪，不进入月度重点
- `medium`：正常观察，月度复查
- `high`：高优先级，可能影响建仓或持仓 thesis

#### 已确认规则

1. 观察池允许“主题级”条目长期存在，例如 AI 算力、游戏出海、券商 beta，不要求绑定单一股票。
2. `review_date` 默认 30 天；高优先级观察项暂不单独缩短为 14 天，后续按使用反馈调整。
3. `watch_type = person` 放入 MVP-1，支持关注人物作为观察对象，但大 V / 专家动态的自动跟踪仍放 MVP-2。
4. 被动发现候选即使被用户连续忽略，也不自动降低该类素材提醒权重；是否调整权重必须由用户显式确认。

#### AI 允许动作

- 根据候选素材提取标的、主题、事件和关联公司。
- 建议 `watch_type`、`related_library_ids`、`related_positions`。
- 把用户的自然语言整理成字段格式。
- 根据材料建议可跟踪指标候选，例如研报数量、订单、流水、财报指标、海外同业变化。
- 检查是否已有重复或相似观察项。

#### AI 禁止动作

- 判断“应该观察”。
- 判断“应该升级建仓”。
- 填写 `watch_reason` 的结论性版本。
- 替用户写最终 `hypothesis`。
- 给观察项排序为“最值得买”。

#### 校验规则

1. `watch_reason`、`hypothesis`、`expected_trigger`、`invalid_condition` 不允许为空。
2. `key_metrics_to_watch` 至少 1 项。
3. `review_date` 不能早于当前日期，默认不超过 30 天；若超过 90 天，需要写原因。
4. 如果 `source_entry = passive_discovery`，必须至少关联 1 条 `related_library_ids` 或保留原始候选素材 id。
5. 如果观察项与现有持仓同板块或同 thesis，系统提示是否关联 `related_positions`。

#### 输出产物

观察池 Checklist 通过后，生成：

```yaml
watchlist_item:
  id: w_20260518_001
  code: "002624"
  name: "完美世界"
  watch_type: stock
  state: watching
  source_entry: passive_discovery
  watch_reason: "异环相关信息流增多，需要跟踪产品节奏与市场反馈"
  hypothesis: "如果异环 PC 端表现和海外反馈持续验证，公司估值体系可能从传统游戏切换到开放世界新品周期"
  key_metrics_to_watch:
    - "异环测试节奏"
    - "海外预约 / 社媒热度"
    - "PC 端流水或下载表现"
  expected_trigger: "产品测试数据和海外反馈持续超预期，且估值仍未充分反映"
  invalid_condition: "测试反馈明显低于预期，或核心上线节奏再次大幅推迟"
  review_date: 2026-06-18
  priority: high
  related_library_ids: ["lib_20260518_003"]
  related_positions: []
  created_at: 2026-05-18
```

#### 与其他场景的关系

| 去向 | 触发条件 | 后续动作 |
|---|---|---|
| 保留观察 | 假设未证伪，但触发条件未出现 | 更新 review_date 和 notes |
| 升级建仓 | expected_trigger 被满足 | 进入 S2 建仓 Checklist |
| 剔除观察 | invalid_condition 被满足 | 状态改为 removed，并写剔除原因 |
| 转入叙事跟踪 | 多维信号增强但还不适合建仓 | MVP-2 生成或关联叙事信号包 |
| 关联持仓巡检 | 与现有持仓 thesis 冲突或补强 | 触发 S4 巡检提醒 |

#### 待后续迭代

1. 高优先级观察项是否需要更短复查周期，先根据 MVP-1 使用反馈再决定。
2. 人物观察项在 MVP-1 只支持手动维护；自动跟踪动态放 MVP-2。

### 16.2 建仓 Checklist

#### 场景定位

建仓 Checklist 是 MVP-1 最关键的决策闸门。

它的目标不是让系统判断“能不能买”，而是强制用户在买入前把以下问题写清楚：

1. 为什么买？
2. 买的是长期主仓还是波段仓？
3. 预期收益来自哪里？
4. 什么情况下证明自己错了？
5. 价格触发目标或止损后，下一步如何再分析？
6. 是否违反仓位、板块、个人禁区等风险护栏？

#### 用户流程

1. 用户从观察池、手动命令、巡检结论或叙事信号包发起建仓。
2. 系统加载观察记录、相关 L1 素材、估值辅助数据、历史相似决策、当前风险暴露。
3. 用户填写建仓 Checklist。
4. 系统检查必填字段、引用素材、风险护栏。
5. 若触发 warning，系统提示但允许继续。
6. 若触发 hard block，用户必须写例外说明。
7. MVP-2 中，若存在未过期叙事信号包，必须先完成 `narrative_stage_assessment`。
8. Checklist 通过后，系统生成建仓 Journal，冻结 data_snapshot。
9. 标的状态进入 `holding`。

#### 字段分层

| 字段 | 类型 | 必填 | 填写者 | 说明 |
|---|---|---|---|---|
| `code` | string | 是 | 用户 / 系统候选 | 股票代码 |
| `name` | string | 是 | 用户 / 系统候选 | 标的名称 |
| `source_entry` | enum | 是 | 系统 | manual / from_watchlist / from_inspection / from_signal_pack |
| `position_type` | enum | 是 | 用户 | core / swing |
| `buy_reason_summary` | text | 是 | 用户 | 一句话买入理由 |
| `investment_thesis` | text | 是 | 用户 | 完整买入逻辑 |
| `expected_return_driver` | list | 是 | 用户 | 预期收益来源，至少 1 项 |
| `target_price` | number / range | 是 | 用户 | 目标价或目标价区间，触发后进入再分析，不自动卖出 |
| `target_price_exception_reason` | text | 条件必填 | 用户 | 目标价不高于现价时必填 |
| `stop_loss` | number / range | 是 | 用户 | 止损/减仓线或区间，触发后进入再分析，不自动卖出 |
| `stop_loss_exception_reason` | text | 条件必填 | 用户 | 止损价不低于现价时必填 |
| `reversal_conditions` | list | 是 | 用户 | 逻辑反转条件，至少 1 项 |
| `position_size_plan` | object | 是 | 用户 | 计划买入仓位、分批计划；MVP-1 必填 `initial_pct` 和 `max_pct` |
| `opportunity_cost_benchmark` | enum | 是 | 用户 | HS300 / CSI_TECH / sector_index / custom |
| `confidence` | enum | 是 | 用户 | low / medium / high |
| `emotion_tag` | enum | 是 | 用户 | calm / anxious / excited / fearful / greedy / fomo |
| `identified_risks` | list | 是 | 用户，AI 可提示 | 已识别风险，至少 1 项 |
| `related_library_ids` | list | 条件必填 | 用户 / 系统候选 | 优先至少关联 1 条依据素材；允许纯个人判断建仓，但必须填写 `no_library_reason` |
| `no_library_reason` | text | 条件必填 | 用户 | 无 L1 素材仍建仓的原因 |
| `risk_guardrail_result` | object | 是 | 系统 | 仓位、板块、个人禁区检查结果 |
| `exception_reason` | text | 条件必填 | 用户 | 触发 hard block 时必填 |
| `narrative_stage_assessment_id` | string | MVP-2 条件必填 | 用户 | 有未过期信号包时必填 |
| `tier_acknowledgement` | boolean | 条件必填 | 用户 | 主要依据素材最高 tier 为 C/D 时须确认 |
| `notes` | text | 否 | 用户 | 其他备注 |

#### 枚举定义

`position_type`：

- `core`：主仓，目标持有 1-3 年或更久
- `swing`：波段仓，目标持有 1 个月-1 年

`expected_return_driver`：

- `earnings_growth`：业绩增长
- `valuation_repair`：估值修复
- `roe_improvement`：ROE 中枢改善
- `narrative_repricing`：叙事重估
- `cycle_reversal`：周期反转
- `capital_flow`：资金面改善
- `event_catalyst`：事件催化
- `other`：其他

`confidence`：

- `low`：假设早期，证据不足，只允许小仓位或观察升级
- `medium`：证据较充分，但仍有关键不确定性
- `high`：核心假设清晰，风险和反转条件明确

`emotion_tag`：

- `calm`：冷静
- `anxious`：焦虑
- `excited`：兴奋
- `fearful`：恐惧
- `greedy`：贪婪
- `fomo`：害怕错过

#### 已确认规则

1. 建仓允许“纯个人判断”而不关联 L1 素材，但必须填写 `no_library_reason`，并写入 Journal。
2. `target_price` / `stop_loss` 允许填写单点或区间。区间用于表达分批止盈、分批减仓、逻辑止损带等场景。
3. `position_size_plan` 在 MVP-1 必须填写 `initial_pct` 和 `max_pct` 两个字段。
4. `emotion_tag = fomo / greedy / anxious` 时，MVP-1 只做二次确认，不做 hard block；后续若复盘证明效果不好，可升级为 hard block。
5. 整体股票仓位上限在 MVP-1 启用，但允许超上限的存量录入。存量超限记录为 `legacy_over_limit`，不强制阻断；新增交易若继续扩大超限，则触发 hard block 和例外说明。

#### `position_size_plan` 字段说明

| 字段 | 中文说明 | 必填 | 示例 |
|---|---|---|---|
| `initial_pct` | 初始建仓后该标的占总资产的比例 | 是 | 5 |
| `max_pct` | 该标的允许持有的最高总仓位比例 | 是 | 10 |
| `add_condition` | 后续加仓条件 | 否 | 测试数据和海外反馈继续验证 |
| `reduce_condition` | 后续减仓条件 | 否 | 目标价区间触发或 thesis 证据弱化 |

#### 价格字段原则

`target_price` 和 `stop_loss` 都必须填写，但它们不是自动交易指令。

触发后的系统行为是：

| 触发项 | 系统动作 | 用户动作 |
|---|---|---|
| 价格达到 `target_price` 单点或区间下沿 | 生成再分析提醒 | 用户重新评估估值、thesis、是否卖出或继续持有 |
| 价格跌破 `stop_loss` 单点或区间上沿 | 生成风险提醒 | 用户检查是否逻辑破坏、是否需要减仓或继续持有 |
| 触发 `reversal_conditions` | 生成强巡检提醒 | 用户必须完成 S4 持仓巡检或 S5 卖出 Checklist |

#### 风险护栏检查

建仓 Checklist 提交前必须运行 M7 风险护栏。

第一版检查：

| 检查项 | warning | hard_block | 处理方式 |
|---|---:|---:|---|
| 单标的仓位 | 10% | 15% | hard block 时必须写例外说明 |
| 单板块集中度 | 30% | 40% | hard block 时必须写例外说明 |
| 整体股票仓位 | 90% | 95% | MVP-1 启用；存量录入允许超限，新增交易扩大超限时触发 hard block |
| 单一 thesis 暴露 | 20% | 30% | 若多个标的依赖同一逻辑，合并计算 |
| 个人禁区 | soft / hard | hard | 按 `personal_redlines.yaml` 执行 |

#### AI 允许动作

- 拉取和整理财务、估值、公告、新闻、研报等事实。
- 从 L1 检索相关素材并提示引用候选。
- 根据用户草稿格式化 Checklist 内容。
- 提醒字段漏填、素材缺失、风险护栏触发。
- 展示历史相似决策和后续结果。
- 建议 `expected_return_driver`、`identified_risks` 候选，但必须由用户确认。

#### AI 禁止动作

- 判断“可以买”。
- 生成最终 `investment_thesis`。
- 填写 `target_price` / `stop_loss`。
- 填写 `confidence`。
- 替用户决定仓位。
- 绕过风险护栏。
- 在叙事场景填写 `narrative_stage`。

#### 校验规则

1. `investment_thesis`、`target_price`、`stop_loss`、`reversal_conditions` 必填。
2. `target_price` 默认应高于当前价；若不高于现价，须填 `target_price_exception_reason`（如左侧布局、再分析触发价等）。
3. `stop_loss` 默认应低于当前价；若不低于现价，须填 `stop_loss_exception_reason`。
4. `expected_return_driver` 至少 1 项。
5. `identified_risks` 至少 1 项。
6. `related_library_ids` 优先至少 1 条；如果没有，必须填写 `no_library_reason`。
7. 主要依据素材最高 tier 为 C 或 D 时，`tier_acknowledgement = true` 必填。
8. 触发 hard block 时，`exception_reason` 必填，且写入 Journal。
9. `emotion_tag = fomo / greedy / anxious` 时，MVP-1 系统弹出二次确认，要求用户补充“是否存在情绪驱动”的自检说明；暂不 hard block。
10. MVP-2 中有未过期叙事信号包时，`narrative_stage_assessment_id` 必填。

### 16.3 持仓巡检 Checklist

#### 场景定位

持仓巡检 Checklist 用来回答一个问题：

> 当初买入这只股票的 thesis，到今天是否仍然成立？

它不是日常看盘，也不是 AI 自动报告。它是用户在系统准备好的事实材料基础上，定期或事件触发地重新判断持仓逻辑。

巡检的重点是把三类内容分开：

1. 事实更新：系统 / AI 可以辅助整理。
2. 用户判断：四维度判断、四象限分类、计划动作必须用户填写。
3. 后续动作：继续持有、加仓、减仓、卖出、继续观察，需要进入对应流程。

#### 触发方式

| 触发方式 | 说明 | MVP-1 |
|---|---|---|
| 手动触发 | 用户主动巡检某只标的 | 是 |
| 月度触发 | 每月对持仓做轻量巡检提醒 | 是 |
| 财报触发 | 财报 / 业绩预告披露后触发 | 是 |
| 价格触发 | 达到 `target_price` / `stop_loss` 后触发 | 是 |
| 反转条件触发 | 建仓 Journal 中的 `reversal_conditions` 被命中 | 是 |
| 叙事信号触发 | MVP-2 中未过期信号包或新信号包触发 | MVP-2 |

#### 用户流程

1. 用户手动触发或系统生成巡检任务。
2. 系统加载建仓 Journal、上次巡检、L1 素材、最新事实数据、风险护栏状态。
3. 系统 / AI 填充事实更新区，标注来源、tier、timestamp。
4. 用户填写四维度判断。
5. 用户选择四象限分类。
6. 用户填写 `planned_action`、置信度、反转条件更新。
7. 若 `planned_action = reduce / exit`，系统提示进入 S5 卖出 Checklist。
8. 若 `planned_action = add`，系统提示进入 S2 建仓 / 加仓 Checklist，并重新跑风险护栏。
9. 系统生成巡检记录，作为后续复盘和 thesis 演进依据。

#### 字段分层

| 字段 | 类型 | 必填 | 填写者 | 说明 |
|---|---|---|---|---|
| `code` | string | 是 | 系统 | 股票代码 |
| `name` | string | 是 | 系统 | 标的名称 |
| `inspection_type` | enum | 是 | 系统 / 用户 | monthly / earnings / price_trigger / reversal_trigger / manual / narrative_trigger |
| `linked_buy_journal_id` | string | 是 | 系统 | 对应建仓 Journal |
| `linked_previous_inspection_id` | string | 否 | 系统 | 上一次巡检记录 |
| `fact_update_summary` | object | 是 | 系统 / AI | 事实更新区，用户审阅 |
| `industry_roe_trend` | enum | 是 | 用户 | improving / stable / deteriorating |
| `free_cash_flow_trend` | enum | 是 | 用户 | improving / stable / deteriorating |
| `market_share_trend` | enum | 是 | 用户 | gaining / stable / losing |
| `core_narrative_status` | enum | 是 | 用户 | intact / shifting / broken |
| `classification` | enum | 是 | 用户 | 四象限分类，见下方中文说明 |
| `planned_action` | enum | 是 | 用户 | hold / add / reduce / exit / keep_watching，见下方中文说明 |
| `confidence` | enum | 是 | 用户 | low / medium / high，见下方中文说明 |
| `thesis_delta` | text | 是 | 用户 | 与原 thesis 相比发生了什么变化 |
| `new_reversal_conditions` | list | 否 | 用户 | 是否更新反转条件 |
| `related_library_ids` | list | 否 | 系统候选 / 用户确认 | 新增引用素材 |
| `risk_guardrail_notes` | object | 否 | 系统 | 当前仓位、板块、整体风险状态 |
| `narrative_stage_assessment_id` | string | MVP-2 条件必填 | 用户 | 有未过期叙事信号包时关联 |
| `industry_roe_unknown_reason` | text | 条件必填 | 用户 | 四维度无法判断时填写 |
| `free_cash_flow_unknown_reason` | text | 条件必填 | 用户 | 同上 |
| `market_share_unknown_reason` | text | 条件必填 | 用户 | 同上 |
| `core_narrative_unknown_reason` | text | 条件必填 | 用户 | 同上 |
| `tier_acknowledgement` | boolean | 条件必填 | 用户 | 事实区主要依据 tier 为 C/D 时确认 |
| `notes` | text | 否 | 用户 | 其他备注 |

#### 事实更新区

`fact_update_summary` 只放事实，不放结论。

MVP-1 建议包含：

| 子字段 | 说明 | AI 可处理 |
|---|---|---|
| `latest_price_change` | 自建仓 / 上次巡检以来涨跌幅 | 是 |
| `valuation_change` | PE/PB/PS 分位变化 | 是 |
| `financial_update` | 财报核心数据变化 | 是 |
| `announcement_update` | 重大公告摘要 | 是 |
| `industry_update` | 行业公开事实变化 | 是 |
| `risk_event_update` | 是否触发风险事件 | 是 |
| `source_list` | 每条事实的 source / tier / timestamp | 是 |

禁止在事实更新区写：

- “逻辑仍然成立”
- “建议持有”
- “可以加仓”
- “已经破坏”
- “市场只是暂时不理解”

#### 四维度判断

用户必须填写四个判断字段：

| 字段 | 判断含义 |
|---|---|
| `industry_roe_trend` | 行业 ROE 中枢是否改善、稳定或恶化 |
| `free_cash_flow_trend` | 公司自由现金流是否改善、稳定或恶化 |
| `market_share_trend` | 公司市场份额是否提升、稳定或下降 |
| `core_narrative_status` | 原始核心叙事是否完整、迁移或破坏 |

四维度判断不允许填写 `unknown`。如果用户暂时无法判断，必须在对应的 `*_unknown_reason` 字段写清楚“为什么无法判断”，并选择当前最接近的状态。这样做的目的不是强迫瞎判，而是避免长期用 unknown 回避关键问题。

#### 四维度枚举说明

`industry_roe_trend` / `free_cash_flow_trend`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `improving` | 改善 | 行业 ROE 或公司自由现金流相对上次巡检/建仓假设变好 |
| `stable` | 稳定 | 没有明显改善或恶化，仍符合原假设 |
| `deteriorating` | 恶化 | 行业 ROE 或公司自由现金流出现趋势性变差 |

`market_share_trend`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `gaining` | 份额提升 | 公司竞争位置增强，份额或关键客户/渠道表现改善 |
| `stable` | 份额稳定 | 竞争位置未见明显变化 |
| `losing` | 份额下降 | 公司竞争位置变弱，份额、渠道、客户或产品表现弱化 |

`core_narrative_status`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `intact` | 叙事完整 | 原始买入逻辑仍成立，没有被关键事实证伪 |
| `shifting` | 叙事迁移 | 原始逻辑未完全破坏，但市场或公司逻辑正在切换，需要更新 thesis |
| `broken` | 叙事破坏 | 原始核心逻辑被关键事实证伪或大幅削弱 |

#### 四象限分类

| 枚举 | 中文 | 含义 |
|---|---|---|
| `low_valuation_logic_intact` | 低估值且逻辑还在 | 估值仍有安全边际，核心 thesis 没有被破坏 |
| `wait_for_style_switch` | 等待风格切换 | 公司基本面尚可，但市场审美或资金偏好暂时不在这里 |
| `cycle_bottom_or_reversal` | 周期低谷 / 逻辑反转中 | 行业或公司处于低谷，但有边际改善或反转迹象 |
| `value_trap_or_broken` | 价值陷阱 / 逻辑已破坏 | 低估值可能不是机会，而是基本面或叙事被破坏的结果 |

注意：分类是用户判断，不是 AI 判断。

#### 计划动作

`planned_action` 只表达用户计划动作，不是系统建议。

| 枚举 | 中文 | 含义 | 后续流程 |
|---|---|---|---|
| `hold` | 继续持有 | 当前不加不减 | 更新下次巡检日期 |
| `add` | 准备加仓 | 用户计划增加仓位 | 进入独立的加仓 Checklist，重新跑风险护栏 |
| `reduce` | 准备减仓 | 用户计划降低仓位 | 进入 S5 卖出 Checklist |
| `exit` | 准备清仓 | 用户计划全部卖出 | 进入 S5 卖出 Checklist |
| `keep_watching` | 继续观察 | 暂不行动，但更新监控重点 | 更新监控重点 |

`confidence`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `low` | 低 | 证据不足，判断不稳定 |
| `medium` | 中 | 有一定证据，但关键变量仍需验证 |
| `high` | 高 | 证据较充分，判断路径清晰 |

#### 已确认规则

1. MVP-1 只做一个统一的巡检 Checklist，不拆轻量 / 深度两个模板。
2. 四维度判断不允许 `unknown`。无法判断时，用 `*_unknown_reason` 解释原因，并选择当前最接近的状态。
3. `planned_action = add` 时进入独立的加仓 Checklist，不复用建仓 Checklist。
4. `classification = value_trap_or_broken` 时允许继续持有，但必须强制说明原因；这是后续归因的重要数据点。
5. 月度巡检默认覆盖全量持仓，但可以低优先级异步执行，允许慢一点统计出来，不要求实时完成。

#### AI 允许动作

- 拉取事实数据、公告、财报、估值、价格变化。
- 对比上次巡检和建仓 Journal，整理事实差异。
- 检索 L1 相关素材。
- 提醒用户哪些反转条件可能被触发。
- 把用户填写的判断整理成 Markdown 报告。

#### AI 禁止动作

- 填写四维度判断。
- 选择四象限分类。
- 填写 `planned_action`。
- 判断“逻辑破坏 / 逻辑还在”。
- 用“长期”“耐心”等模糊词解释资本效率问题。

#### 校验规则

1. 四维度判断必须全部填写，不允许 `unknown`；无法判断时必须填写对应 `*_unknown_reason`。
2. `classification` 必填，且必须由用户填写。
3. `planned_action` 必填，且必须由用户填写。
4. 如果 `planned_action = add`，必须进入独立的加仓 Checklist，不能直接执行。
5. 如果 `planned_action = reduce / exit`，必须进入卖出 Checklist，不能直接关闭持仓。
6. 如果事实更新区显示触发 `reversal_conditions`，但用户选择 `hold`，必须填写“为什么仍然持有”。
7. 如果 `classification = value_trap_or_broken` 但 `planned_action = hold`，必须填写继续持有原因，供后续归因使用。
8. 如果分类从上次巡检发生变化，必须填写 `thesis_delta`。
9. MVP-2 中有未过期叙事信号包时，`narrative_stage_assessment_id` 必填。
10. 事实区主要依据 tier 为 C 或 D 时，`tier_acknowledgement = true` 必填。

### 16.4 加仓 Checklist

#### 场景定位

加仓 Checklist 是建仓后的二次高风险决策。

它和建仓的区别是：

| 维度 | 建仓 | 加仓 |
|---|---|---|
| 决策基础 | 从 0 到 1 建立 thesis | 在已有 thesis 和真实持仓结果上增加暴露 |
| 主要风险 | 买错标的 | 在错误 thesis 上越陷越深 |
| 关键问题 | 为什么买？ | 为什么现在要加？原 thesis 是增强了，还是只是想摊低成本？ |
| 复盘重点 | 建仓判断是否成立 | 加仓是否提升收益质量，还是放大错误 |

加仓 Checklist 的目标不是阻止加仓，而是强制区分三件事：

1. thesis 增强后的理性加仓。
2. 价格下跌后的摊低成本。
3. 情绪驱动的补仓、报复性交易或 FOMO。

#### 触发方式

| 触发方式 | 说明 |
|---|---|
| 巡检触发 | S4 中 `planned_action = add` |
| 价格触发 | 股价跌到预设加仓区间或回调区间 |
| thesis 触发 | 原 thesis 的关键证据增强 |
| 叙事触发 | MVP-2 中叙事信号包增强，用户完成阶段判断 |
| 手动触发 | 用户主动发起加仓 |

#### 用户流程

1. 用户从巡检、价格提醒、叙事信号包或手动命令发起加仓。
2. 系统加载原建仓 Journal、历次巡检、当前持仓仓位、收益、风险护栏状态。
3. 系统对比原 thesis 与当前事实，整理“增强 / 削弱 / 未变化”的事实材料。
4. 用户填写加仓 Checklist。
5. 系统运行风险护栏，重点检查单标的、单板块、整体股票仓位、单一 thesis 暴露、报复性加仓红线。
6. MVP-2：若有未过期叙事信号包，须先完成 `narrative_stage_assessment` 并填写 `narrative_stage_assessment_id`。
7. 若触发 hard block，用户必须写例外说明。
8. Checklist 通过后生成加仓 Journal、新 `lot` 及 `data_snapshot`。

#### 字段分层

| 字段 | 类型 | 必填 | 填写者 | 说明 |
|---|---|---|---|---|
| `code` | string | 是 | 系统 | 股票代码 |
| `name` | string | 是 | 系统 | 标的名称 |
| `linked_buy_journal_id` | string | 是 | 系统 | 原建仓 Journal |
| `linked_inspection_id` | string | 条件必填 | 系统 | 若由巡检触发，必须关联巡检记录 |
| `add_trigger` | enum | 是 | 用户 | thesis_strengthened / price_pullback / valuation_better / risk_reward_better / signal_pack / manual |
| `add_reason_summary` | text | 是 | 用户 | 一句话加仓理由 |
| `thesis_change` | enum | 是 | 用户 | strengthened / unchanged / weakened_but_price_compensates |
| `thesis_change_explanation` | text | 是 | 用户 | 原 thesis 相比建仓时发生了什么变化 |
| `new_evidence` | list | 是 | 用户，AI 可建议 | 支持加仓的新证据，至少 1 项 |
| `counter_evidence` | list | 是 | 用户，AI 可建议 | 反向证据，至少 1 项；若没有必须写“未发现” |
| `current_position_pct` | number | 是 | 系统 | 加仓前该标的仓位 |
| `add_pct` | number | 是 | 用户 | 本次计划增加的仓位比例 |
| `position_pct_after` | number | 是 | 系统 | 加仓后该标的仓位 |
| `max_pct_after_add` | number | 是 | 用户 | 本次加仓后仍愿意接受的最高仓位 |
| `average_cost_after` | number | 是 | 系统 | 加仓后成本 |
| `target_price` | number / range | 是 | 用户 | 加仓后的目标价或区间，可沿用或更新 |
| `stop_loss` | number / range | 是 | 用户 | 加仓后的止损/减仓线或区间，可沿用或更新 |
| `reversal_conditions_update` | list | 是 | 用户 | 是否更新反转条件；不更新也要写“沿用原条件” |
| `emotion_tag` | enum | 是 | 用户 | calm / anxious / excited / fearful / greedy / fomo |
| `is_averaging_down` | boolean | 是 | 系统 / 用户确认 | 是否属于下跌后摊低成本 |
| `averaging_down_reason` | text | 条件必填 | 用户 | 若是摊低成本，必须说明为什么不是报复性加仓 |
| `risk_guardrail_result` | object | 是 | 系统 | 风险护栏结果 |
| `exception_reason` | text | 条件必填 | 用户 | 触发 hard block 时必填 |
| `related_library_ids` | list | 条件必填 | 用户 / 系统候选 | 优先引用新证据素材；无素材则写原因 |
| `no_library_reason` | text | 条件必填 | 用户 | 无 L1 素材仍加仓的原因 |
| `narrative_stage_assessment_id` | string | MVP-2 条件必填 | 用户 | 有未过期信号包时必填 |
| `tier_acknowledgement` | boolean | 条件必填 | 用户 | 主要依据 tier 为 C/D 时确认 |
| `notes` | text | 否 | 用户 | 其他备注 |

#### 枚举说明

`add_trigger`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `thesis_strengthened` | thesis 增强 | 原买入逻辑被新证据强化 |
| `price_pullback` | 价格回调 | 价格下跌到计划区间，但必须确认 thesis 未削弱 |
| `valuation_better` | 估值更优 | 估值性价比改善，但不能单独作为加仓理由 |
| `risk_reward_better` | 风险收益比改善 | 上行空间 / 下行风险结构比建仓时更好 |
| `signal_pack` | 叙事信号包触发 | MVP-2 中信号包增强且用户已完成阶段判断 |
| `manual` | 手动触发 | 用户主动发起，需要写清原因 |

`thesis_change`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `strengthened` | thesis 增强 | 新证据让原假设更可信 |
| `unchanged` | thesis 未变 | 原假设没有增强，只是价格、估值或仓位结构变化 |
| `weakened_but_price_compensates` | thesis 变弱但价格补偿 | 逻辑弱化，但用户认为价格已充分补偿风险，必须强制说明 |

#### 反报复性加仓规则

加仓最危险的场景是“亏损后为了摊低成本而扩大错误”。

MVP-1 规则：

| 条件 | 系统处理 |
|---|---|
| 当前持仓浮亏超过 10%，且本次 `add_trigger = price_pullback` | 二次确认 |
| 当前持仓浮亏超过 20%，且 `thesis_change != strengthened` | hard block，需要例外说明 |
| 距上次买入 / 加仓少于 14 天，且再次加仓 | warning，需要说明节奏 |
| `emotion_tag = fomo / greedy / anxious` | 二次确认 |
| `thesis_change = weakened_but_price_compensates` | hard block，需要例外说明 |

#### 已确认规则

1. 当前持仓浮亏超过 20%，且 thesis 未增强时 hard block，初版暂不修改阈值；后续通过实践复盘决定是否调整为 15% 或 30%。
2. 距上次买入 / 加仓少于 14 天再次加仓，MVP-1 只做 warning，不做 hard block。原因是如果 thesis 快速验证，合理加仓节奏可能很快；系统只要求用户说明节奏，并在后续复盘中单独归因。
3. `counter_evidence` 初版必须填写至少 1 项；如果用户认为没有反向证据，写“未发现”即可。
4. `thesis_change = unchanged` 时允许加仓，但必须说明为什么 thesis 未增强仍值得增加暴露。
5. 加仓后的收益归因必须和原建仓仓位分开计算，便于复盘“加仓动作本身”是否提升收益质量。

#### 风险护栏检查

加仓必须重新运行 M7 风险护栏。

| 检查项 | 处理 |
|---|---|
| 单标的仓位超过 warning / hard block | 按 M7 规则处理 |
| 单板块集中度超过 warning / hard block | 按 M7 规则处理 |
| 整体股票仓位超过 warning / hard block | 存量超限允许存在；新增加仓扩大超限时 hard block |
| 单一 thesis 暴露超过上限 | 合并计算同一逻辑下的多个标的 |
| 个人禁区命中“报复性加仓” | hard block，需要例外说明 |

#### AI 允许动作

- 对比建仓 Journal、上次巡检和当前事实，整理变化。
- 检索支持和反对加仓的新素材。
- 计算当前仓位、加仓后仓位、加仓后成本。
- 提醒是否属于摊低成本、是否触发风险护栏。
- 格式化用户填写的 thesis 变化说明。

#### AI 禁止动作

- 判断“应该加仓”。
- 生成最终加仓理由。
- 替用户判断 thesis 是否增强。
- 替用户填写 `add_pct` / `max_pct_after_add`。
- 绕过报复性加仓规则。
- 用“跌多了会反弹”作为加仓理由。

#### 校验规则

1. `add_reason_summary`、`thesis_change_explanation` 必填。
2. `new_evidence` 至少 1 项。
3. `counter_evidence` 至少 1 项；如果没有，必须显式写“未发现”。
4. `add_pct` 必须大于 0。
5. `position_pct_after` 不得超过 `max_pct_after_add`。
6. 若 `is_averaging_down = true`，`averaging_down_reason` 必填。
7. 若 `thesis_change = unchanged`，允许加仓，但必须说明为什么在 thesis 未增强时仍值得增加暴露。
8. 若 `thesis_change = weakened_but_price_compensates`，触发 hard block，必须写例外说明。
9. 若触发任何 hard block，`exception_reason` 必填并写入 Journal。
10. `target_price` / `stop_loss` 必须重新确认，可沿用原值但必须显式选择“沿用”。
11. MVP-2 中有未过期叙事信号包时，`narrative_stage_assessment_id` 必填。
12. 主要依据素材最高 tier 为 C 或 D 时，`tier_acknowledgement = true` 必填。

### 16.5 卖出 / 减仓 Checklist

#### 场景定位

卖出 / 减仓 Checklist 用来记录一次退出或降低风险暴露的决策。

它的目标不是判断“该不该卖”，而是强制用户在卖出前写清楚：

1. 卖出的直接原因是什么？
2. 原 thesis 是被验证、部分验证、证伪，还是时间不足？
3. 这次卖出是理性执行，还是恐慌、厌倦、换股冲动？
4. 收益来自哪里，亏损来自哪里？
5. 这次交易给后续 Checklist / redlines / 风险规则留下什么教训？

卖出不是交易结束，而是复盘数据开始变得有价值的时刻。

#### 触发方式

| 触发方式 | 说明 |
|---|---|
| 巡检触发 | S4 中 `planned_action = reduce / exit` |
| 价格触发 | 达到 `target_price`、跌破 `stop_loss` 或进入目标/止损区间 |
| 反转条件触发 | 建仓或加仓 Journal 中的反转条件被命中 |
| 风险护栏触发 | 仓位、板块、整体风险或个人禁区要求降低暴露 |
| 手动触发 | 用户主动发起卖出 / 减仓 |

#### 用户流程

1. 用户从巡检、价格提醒、风险护栏或手动命令发起卖出 / 减仓。
2. 系统加载建仓 Journal、加仓 Journal、历次巡检、当前收益、相对收益、风险护栏状态。
3. 系统计算本次卖出涉及的仓位批次、成本、收益和基准对比。
4. 用户填写卖出 / 减仓 Checklist。
5. 系统检查是否触发个人禁区，例如恐慌止损、短期情绪化换股、报复性交易。
6. Checklist 通过后生成卖出 Journal。
7. 若全部卖出，持仓状态变为 `closed`；若部分卖出，更新剩余仓位和后续监控重点。
8. 系统生成单笔归因记录，进入 S6 周期性复盘汇总。

#### 字段分层

| 字段 | 类型 | 必填 | 填写者 | 说明 |
|---|---|---|---|---|
| `code` | string | 是 | 系统 | 股票代码 |
| `name` | string | 是 | 系统 | 标的名称 |
| `sell_type` | enum | 是 | 用户 | reduce / exit |
| `sell_trigger` | enum | 是 | 用户 | target_reached / stop_loss_reached / thesis_broken / valuation_overheat / switch_opportunity / risk_guardrail / manual |
| `sell_reason` | enum | 是 | 用户 | 见下方枚举说明 |
| `sell_reason_detail` | text | 是 | 用户 | 卖出原因的具体说明 |
| `linked_buy_journal_ids` | list | 是 | 系统 | 关联建仓 / 加仓 Journal |
| `linked_inspection_id` | string | 条件必填 | 系统 | 若由巡检触发，必须关联巡检记录 |
| `sell_pct` | number | 是 | 用户 | 本次计划卖出的仓位比例 |
| `position_pct_after` | number | 是 | 系统 | 卖出后剩余仓位 |
| `thesis_result` | enum | 是 | 用户 | validated / partially_validated / invalidated / not_enough_time |
| `thesis_result_explanation` | text | 是 | 用户 | 原 thesis 的验证结果说明 |
| `return_result` | object | 是 | 系统 | 绝对收益、相对收益、持有期收益 |
| `attribution` | object | 是 | 用户 + 系统 | 收益 / 亏损归因 |
| `emotion_tag` | enum | 是 | 用户 | calm / anxious / excited / fearful / greedy / fomo / tired |
| `is_panic_sell` | boolean | 是 | 系统 / 用户确认 | 是否可能属于恐慌卖出 |
| `is_switch_trade` | boolean | 是 | 用户 | 是否为了换股 / 切换机会 |
| `switch_target` | string | 条件必填 | 用户 | 若为换股，填写目标标的或主题 |
| `lesson` | text | 是 | 用户 | 本次教训 |
| `rule_change_suggestion` | text | 否 | 用户 | 是否建议修改 Checklist / redlines / 风险规则 |
| `risk_guardrail_result` | object | 否 | 系统 | 风险护栏检查结果 |
| `related_library_ids` | list | 否 | 用户 / 系统候选 | 卖出依据素材 |
| `notes` | text | 否 | 用户 | 其他备注 |

#### 枚举说明

`sell_type`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `reduce` | 减仓 | 降低部分仓位，仍保留持仓 |
| `exit` | 清仓 | 全部卖出，状态进入 closed |

`sell_trigger`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `target_reached` | 目标价触发 | 达到目标价或目标价区间 |
| `stop_loss_reached` | 止损线触发 | 跌破止损/减仓线或区间 |
| `thesis_broken` | thesis 破坏 | 原买入逻辑被关键事实证伪 |
| `valuation_overheat` | 估值过热 | 估值已明显超过原预期或风险收益变差 |
| `switch_opportunity` | 换股机会 | 用户认为有更好机会，需要腾挪资金 |
| `risk_guardrail` | 风险护栏触发 | 仓位、集中度、个人禁区等要求降低暴露 |
| `manual` | 手动触发 | 其他主动原因 |

`sell_reason`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `logic_broken` | 逻辑破坏 | 原 thesis 被证伪或关键假设不再成立 |
| `target_achieved` | 目标达成 | 达到目标价、目标收益或原计划卖点 |
| `valuation_too_high` | 估值过高 | 估值透支，风险收益比下降 |
| `risk_reduction` | 降低风险 | 仓位、板块、账户风险过高 |
| `opportunity_switch` | 换股 / 换机会 | 资金转向更优机会 |
| `stop_loss` | 止损 | 触发止损或减仓线 |
| `time_cost` | 时间成本过高 | thesis 未破坏但资本效率低 |
| `other` | 其他 | 需写明原因 |

`thesis_result`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `validated` | 已验证 | 原 thesis 基本兑现 |
| `partially_validated` | 部分验证 | 部分假设成立，部分未达预期 |
| `invalidated` | 已证伪 | 核心假设被事实证伪 |
| `not_enough_time` | 时间不足 | 持有时间不足，无法判断 thesis 对错 |

`emotion_tag`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `calm` | 冷静 | 按计划或规则执行 |
| `anxious` | 焦虑 | 担心继续亏损或机会流失 |
| `excited` | 兴奋 | 因盈利或行情亢奋而卖出 |
| `fearful` | 恐惧 | 明显受市场下跌或亏损影响 |
| `greedy` | 贪婪 | 因想换更高弹性机会而卖出 |
| `fomo` | 害怕错过 | 为追逐新机会而卖出 |
| `tired` | 厌倦 | 因长期不涨、心态疲惫而卖出 |

#### 归因字段

卖出时必须生成单笔归因。加仓批次和原建仓批次要分开计算。

MVP-1 中，卖出归因的批次收益采用 lot 单独跟踪作为硬要求。每一次建仓、加仓都形成独立 lot；卖出时需要明确本次卖出对应哪些 lot，并分别计算收益。这是后续判断“加仓动作本身是否有效”的基础。

`attribution` 建议包含：

| 字段 | 中文 | 填写方式 |
|---|---|---|
| `price_return` | 价格收益 | 系统计算 |
| `benchmark_excess_return` | 相对基准超额收益 | 系统计算 |
| `holding_days` | 持有天数 | 系统计算 |
| `thesis_contribution` | thesis 贡献 | 用户填写 |
| `valuation_contribution` | 估值变化贡献 | 系统辅助，用户确认 |
| `market_beta_contribution` | 市场 beta 贡献 | 系统辅助 |
| `narrative_contribution` | 叙事重估贡献 | 用户填写，MVP-2 可辅助 |
| `execution_quality` | 执行质量 | 用户填写 |
| `mistake_type` | 错误类型 | 用户填写，可为空 |
| `result_category` | 结果分类 | 用户填写 |

`result_category`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `good_process_good_result` | 过程好，结果好 | 决策和结果都符合预期 |
| `good_process_bad_result` | 过程好，结果不好 | 当时没有错，但结果不利 |
| `bad_process_good_result` | 过程差，结果好 | 运气盈利，需要警惕 |
| `bad_process_bad_result` | 过程差，结果差 | 明确需要修正 |

#### 已确认规则

1. `lesson` 每次卖出 / 减仓都必须填写，即使只是小幅减仓。
2. `sell_reason = time_cost` 时必须单独触发机会成本归因。
3. `result_category` 四分类初版保持当前定义。
4. 卖出归因的批次收益采用 lot 单独跟踪，作为 MVP-1 硬要求。
5. `emotion_tag = tired` 进入 MVP-1 枚举，用于记录长期持有后的厌倦卖出。

#### 反情绪化卖出规则

| 条件 | 系统处理 |
|---|---|
| 当日大盘跌幅超过 3%，且 `sell_reason = stop_loss` | warning，需要说明是否恐慌 |
| 持仓浮亏超过 20%，且 `thesis_result != invalidated` | 二次确认 |
| `emotion_tag = fearful / anxious / tired / fomo` | 二次确认 |
| `is_switch_trade = true` 且未填写 `switch_target` | 不允许提交 |
| `sell_reason = opportunity_switch` 但未完成新标的观察或建仓 Checklist | warning |

#### AI 允许动作

- 计算收益、相对收益、持有期、批次收益。
- 汇总建仓以来的 Journal、巡检、加仓、风险例外。
- 对照原始 thesis 和反转条件，列出事实差异。
- 整理用户填写的归因和教训。
- 提醒是否可能触发恐慌卖出、换股冲动、厌倦卖出。

#### AI 禁止动作

- 判断“应该卖出”。
- 填写 `sell_reason`。
- 填写 `thesis_result`。
- 判断“卖早了 / 卖晚了”。
- 用短期价格走势替代 thesis 判断。
- 替用户修改 redlines 或 Checklist。

#### 校验规则

1. `sell_type`、`sell_trigger`、`sell_reason`、`sell_reason_detail` 必填。
2. `thesis_result`、`thesis_result_explanation` 必填。
3. `lesson` 必填，即使本次是盈利交易也必须写。
4. 若 `sell_type = reduce`，`position_pct_after` 必须大于 0。
5. 若 `sell_type = exit`，`position_pct_after` 必须等于 0。
6. 若 `is_switch_trade = true`，`switch_target` 必填。
7. 若 `sell_reason = other`，`sell_reason_detail` 至少 20 字。
8. 若 `thesis_result = invalidated`，必须选择或填写至少 1 个 `mistake_type`。
9. 若触发反情绪化卖出 warning，必须填写情绪自检说明。
10. 卖出后必须生成单笔归因记录，进入 S6 周期复盘。
11. 若 `sell_reason = time_cost`，必须生成机会成本归因记录，对比用户选择的 benchmark。
12. 卖出必须关联到具体 lot；如果无法精确匹配，必须标记为 `lot_match_pending`，后续补齐。

卖出 / 减仓 Checklist 通过后，生成：

### 16.6 周期性复盘 Checklist

#### 场景定位

周期性复盘 Checklist 用来把单笔交易、持仓巡检、加仓、卖出归因汇总成个人投资系统的迭代输入。

它不是简单总结“赚了多少钱”，而是回答：

1. 哪些收益来自正确 thesis，哪些来自市场 beta 或运气？
2. 哪些亏损是流程错误，哪些只是好过程坏结果？
3. 哪些加仓提升了收益质量，哪些放大了错误？
4. 哪些情绪标签、信息源 tier、风险例外和结果有关？
5. 是否需要修改 Checklist、personal_redlines 或 risk_rules？

#### 复盘层级

| 层级 | 频率 | 重点 | MVP-1 |
|---|---|---|---|
| 单笔归因 | 每次卖出 / 减仓后 | 本次动作收益、thesis 结果、教训 | 是 |
| 月度复盘 | 每月 | 行为纪律、巡检完成度、风险例外、持仓状态 | 是 |
| 季度复盘 | 每季度 | 收益归因汇总、策略表现、规则修改 | 是 |
| 年度复盘 | 每年 | 投资系统升级、长期模式画像 | MVP-2 增强 |

#### 用户流程

1. 系统按月 / 季度生成复盘任务。
2. 系统汇总本周期内的建仓、加仓、巡检、卖出、风险例外、L1 引用、监控触发。
3. 系统生成事实统计区：收益、相对基准、lot 归因、Checklist 完成度、情绪标签分布、风险例外。
4. 系统扫描候选错误模式，但不写最终结论。
5. 用户确认哪些是真问题、哪些是好过程坏结果。
6. 用户填写本期复盘 Checklist。
7. 若需要修改 Checklist / redlines / risk_rules，系统生成规则变更 Journal。
8. 复盘报告归档，作为后续建仓、加仓、卖出时的历史参考。

#### 字段分层

| 字段 | 类型 | 必填 | 填写者 | 说明 |
|---|---|---|---|---|
| `review_id` | string | 是 | 系统 | 复盘记录 id |
| `review_type` | enum | 是 | 用户 / 系统 | monthly / quarterly / yearly / ad_hoc |
| `period_start` | date | 是 | 系统 | 复盘开始日期 |
| `period_end` | date | 是 | 系统 | 复盘结束日期 |
| `performance_summary` | object | 是 | 系统 | 收益、基准、持仓变化 |
| `lot_attribution_summary` | object | 是 | 系统 | 建仓 / 加仓 lot 的收益归因汇总 |
| `behavior_summary` | object | 是 | 系统 | Checklist 完成度、风险例外、巡检完成度 |
| `emotion_summary` | object | 是 | 系统 | 情绪标签与结果统计 |
| `source_tier_summary` | object | 是 | 系统 | 信息源 tier 与决策结果统计 |
| `confirmed_patterns` | list | 是 | 用户 | 用户确认的错误 / 有效模式 |
| `good_process_bad_result_cases` | list | 是 | 用户 | 好过程坏结果案例 |
| `bad_process_good_result_cases` | list | 是 | 用户 | 坏过程好结果案例 |
| `rule_change_decisions` | list | 否 | 用户 | 是否修改 Checklist / redlines / risk_rules |
| `next_period_focus` | list | 是 | 用户 | 下个周期重点改进项 |
| `notes` | text | 否 | 用户 | 其他备注 |

#### 枚举说明

`review_type`：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `monthly` | 月度复盘 | 重点看行为纪律和持仓状态 |
| `quarterly` | 季度复盘 | 重点看收益归因和规则演进 |
| `yearly` | 年度复盘 | 重点看投资系统长期升级 |
| `ad_hoc` | 临时复盘 | 大幅回撤、重大错误或重要阶段结束后手动触发 |

`confirmed_patterns` 中的模式类型：

| 枚举 | 中文 | 含义 |
|---|---|---|
| `low_valuation_trap` | 低估值陷阱 | 因低估值忽视基本面恶化 |
| `premature_sell` | 过早卖出 | thesis 未破坏但过早退出 |
| `revenge_add` | 报复性加仓 | 亏损后为摊低成本扩大错误 |
| `fomo_buy` | FOMO 买入 | 害怕错过而买入 |
| `panic_sell` | 恐慌卖出 | 市场下跌或亏损驱动卖出 |
| `thesis_drift` | thesis 漂移 | 买入逻辑事后被悄悄改写 |
| `missed_narrative` | 错过叙事 | MVP-2 扫描错过的新叙事周期 |
| `good_discipline` | 有效纪律 | 某条规则被证明有价值 |
| `other` | 其他 | 用户自定义 |

#### 已确认规则

1. 月度复盘也必须做 lot 归因，不只季度复盘强制。
2. `confirmed_patterns` 每期必须确认，允许选择已有模式，也允许用 `other` 自定义填写。
3. 规则变更 Journal 需要用户二次确认，避免复盘时冲动改规则。
4. 年度复盘放入 MVP-2，不进入 MVP-1。

#### 事实统计区

系统可自动生成但用户需要审阅：

| 区域 | 内容 |
|---|---|
| `performance_summary` | 本期绝对收益、相对基准、已实现收益、浮盈亏 |
| `lot_attribution_summary` | 每个 lot 的收益、持有期、相对收益、对应动作 |
| `behavior_summary` | 建仓 / 加仓 / 巡检 / 卖出 Checklist 完成情况 |
| `risk_exception_summary` | 触发 warning / hard block / exception 的次数和结果 |
| `emotion_summary` | 不同 emotion_tag 下的收益和动作统计 |
| `source_tier_summary` | 不同信息源 tier 对应的决策结果 |
| `time_cost_summary` | 因时间成本卖出的案例和机会成本 |

#### 用户判断区

用户必须填写：

1. 本期最重要的 1-3 个正确动作。
2. 本期最重要的 1-3 个错误动作。
3. 哪些坏结果属于“当时没错，只是结果不好”。
4. 哪些好结果其实过程很差，只是运气好。
5. 下个周期要新增、删除或强化哪条规则。

#### 规则变更机制

如果复盘后要修改规则，必须生成规则变更 Journal。

规则变更包括：

- Checklist 字段调整。
- `personal_redlines.yaml` 增删改。
- `risk_rules.yaml` 阈值调整。
- 情绪标签处理方式变化。
- 叙事信号包阈值变化。

规则变更 Journal 必须包含：

| 字段 | 说明 |
|---|---|
| `change_target` | checklist / personal_redlines / risk_rules / narrative_signals |
| `change_type` | add / update / remove |
| `before` | 修改前 |
| `after` | 修改后 |
| `reason` | 为什么修改 |
| `evidence_review_id` | 来自哪次复盘 |

#### AI 允许动作

- 汇总统计和生成表格。
- 扫描候选错误模式。
- 找出相似历史交易。
- 对比规则变更前后的结果。
- 把用户确认后的复盘结论整理成 Markdown。

#### AI 禁止动作

- 替用户确认错误模式。
- 自动修改 Checklist / redlines / risk_rules。
- 把亏损直接等同于错误。
- 把盈利直接等同于正确。
- 用鼓励性语言掩盖机会成本。

#### 校验规则

1. 月度 / 季度复盘必须填写 `next_period_focus`。
2. 月度 / 季度复盘都必须包含 lot 归因汇总。
3. 如果本期有卖出 / 减仓，必须引用对应单笔归因。
4. 如果本期有 hard block exception，必须在复盘中逐条确认结果。
5. `confirmed_patterns` 必须至少 1 项；如果没有命中已有模式，必须选择 `other` 并自定义填写。
6. 如果用户确认某个错误模式，必须决定是否修改规则；可以选择不修改，但要写原因。
7. 任何规则修改必须生成规则变更 Journal，且需要用户二次确认后生效。
8. `good_process_bad_result_cases` 和 `bad_process_good_result_cases` 允许为空，但季度复盘必须显式确认“无”。

## 十八、M7 风险护栏功能边界

### 18.1 定位

M7 风险护栏不是收益优化器，也不是组合管理系统。

它的定位是：

> 在建仓、加仓、卖出、复盘等关键动作前，检查是否触发仓位、集中度、个人禁区和情绪风险，并强制留下例外说明。

M7 的核心价值不是“禁止用户犯错”，而是让每一次越界都变成可复盘的数据。

### 18.2 MVP-1 必做

| 功能 | 说明 |
|---|---|
| 单标的仓位检查 | warning 10%，hard block 15% |
| 单板块集中度检查 | warning 30%，hard block 40% |
| 整体股票仓位检查 | warning 90%，hard block 95%；存量超限允许录入 |
| 单一 thesis 暴露检查 | warning 20%，hard block 30% |
| 个人禁区检查 | 基于 `personal_redlines.yaml` |
| hard block 例外说明 | 触发后必须写 `exception_reason` |
| 风险例外入 Journal | 所有例外进入后续复盘 |
| 存量超限标记 | 首次录入历史持仓时允许 `legacy_over_limit` |

### 18.3 MVP-1 不做

| 不做项 | 原因 |
|---|---|
| 机构级 VaR / 波动率模型 | 复杂度高，不符合个人 MVP 目标 |
| 自动再平衡 | 决策权必须在用户 |
| 自动卖出 | 产品不做自动交易 |
| 精细行业因子暴露 | 阶段 3/4 后再评估 |
| 衍生品风险模型 | 当前产品范围不覆盖 |

### 18.4 第一版阈值

| 规则 | warning | hard_block | 说明 |
|---|---:|---:|---|
| 单标的仓位 | 10% | 15% | 主动投资允许一定集中，但超过 15% 必须写例外 |
| 单板块集中度 | 30% | 40% | 板块轮动可集中，但超过 40% 风险过高 |
| 整体股票仓位 | 90% | 95% | 防止满仓无调整空间；存量超限允许录入 |
| 单一 thesis 暴露 | 20% | 30% | 多只股票依赖同一逻辑时合并计算 |

### 18.5 `legacy_over_limit` 规则

用户首次录入现有持仓时，可能已经超过 MVP-1 风险阈值。

处理规则：

1. 允许录入，不阻断。
2. 标记为 `legacy_over_limit`。
3. 不要求立即整改。
4. 后续新增交易如果进一步扩大超限，触发 hard block。
5. 季度复盘中汇总存量超限项，但是否生成整改计划后续再定。

### 18.6 个人禁区

`personal_redlines.yaml` 第一版建议支持：

| 字段 | 说明 |
|---|---|
| `id` | 禁区 id |
| `rule` | 禁区描述 |
| `severity` | soft / hard |
| `trigger_condition` | 触发条件 |
| `related_scenarios` | buy / add / sell / review |
| `exception_allowed` | 是否允许例外 |

MVP-1 个人禁区配置（`personal_redlines.yaml`）：

| id | rule | severity | 触发场景 | MVP-1 默认 |
|---|---|---|---|---|
| r001 | 不在 thesis 未增强时因亏损扩大而报复性加仓 | hard | add | **enabled** |
| r002 | 不在大盘单日暴跌时仅因恐慌止损 | soft | sell | **enabled** |
| r003 | 不用“低估值”单独作为建仓或加仓理由 | soft | buy / add | **enabled** |
| r004 | 不在无素材、无反转条件时重仓买入 | hard | buy | **enabled** |
| r005 | 不因厌倦长期不涨而卖出，除非明确 time_cost 归因 | soft | sell | **enabled** |
| r006 | 不在没有 `target_price` / `stop_loss` / `reversal_conditions` 的情况下提交建仓 | hard | buy | disabled（Checklist 校验已覆盖，可作双保险） |
| r007 | 不把“长期持有”作为回避机会成本归因的理由 | soft | review / sell | disabled |
| r008 | 不在 `emotion_tag = fomo` 时扩大仓位，除非完成二次确认和例外说明 | soft | buy / add | disabled（MVP-1 二次确认已覆盖） |
| r009 | 不在 thesis 已漂移但未更新 Journal 的情况下继续加仓 | hard | add | disabled |
| r010 | 不把单一叙事信号当作完整 thesis，至少需要多维证据或明确说明例外 | soft | buy / add | disabled |
| r011 | 不在单一 thesis 暴露超过 hard block 后继续新增同逻辑仓位，除非写例外说明 | hard | buy / add | disabled（M7 仓位规则已覆盖） |
| r012 | 不因“已亏很多”而拒绝承认 thesis 破坏；若 `classification = value_trap_or_broken` 且继续持有，必须说明 | soft | inspect / review | disabled |

#### 已确认规则

1. MVP-1 **默认启用 r001–r005**；r006–r012 **预置在 yaml 中且 `enabled: false`**，用户可在复盘后手动开启。
2. hard block 例外说明中的 `expected_compensation` 必填。
3. soft warning 也记录到 Journal，不只记录 hard block exception。
4. 存量超限只做风险标记，不生成强制整改计划。

### 18.7 例外说明 — hard / soft 拦截差异（2026-05-22 Review 修订，见 [docs/06 §D5](06-架构Review决议.md)）

为避免「例外说明形同虚设」与「用户绕过系统直接去券商 App」两类极端，hard / soft 的拦截行为显式分级：

| severity | 拦截行为 | exception_json 字段最低要求 |
|---|---|---|
| `hard` | **强拦截**：必须填写完整例外说明才能 Submit | `triggered_rule_id` + `exception_reason`（**≥ 80 字**）+ `expected_compensation`（必填） + `review_date`（必填）+ **至少 1 条 S/A tier `library_item_id`** 作为依据 + `confirm_text="我已知悉本次例外永久记入 Journal"` |
| `soft` | **软警示**：仅显示警告并记录"warning ack"，不强制完整例外说明 | `acked: true` + `ack_note`（可选，建议 ≥ 20 字） |

> 字段含义：
> - `triggered_rule_id`：触发的规则 id（M7 仓位规则 `m7_*` 或 `personal_redlines.yaml` 中的 `r*`）。
> - `exception_reason`：为什么这次要例外（**hard 时强制 ≥ 80 字**，避免一句话糊弄）。
> - `expected_compensation`：这次例外带来的预期补偿（业绩拐点 / 估值修复 / 流动性窗口等），用于事后归因。
> - `review_date`：何时主动复查这个例外（建议 ≤ 90 天）。
> - S/A tier 引用：hard 时必须挂至少 1 条 S（公告）或 A（结构化金融数据）证据，C/D 不可作主依据。

**MVP-2 违规绕过检测**（H14 复盘扫描）：扫描"hard block 后 7 天内的 Journal 缺口"，对照券商对账单提示用户"本月可能有未记录交易"，作为反"绕过系统"的兜底信号。

### 18.8 AI 边界

AI 允许：

- 汇总触发了哪些规则。
- 解释规则含义。
- 检索历史例外结果。
- 整理例外说明格式。

AI 禁止：

- 判断“这次可以例外”。
- 帮用户绕过 hard block。
- 自动降低阈值。
- 自动修改个人禁区。

### 18.9 待后续迭代

1. soft warning 记录到 Journal 后，复盘报告中如何聚合展示，放到 M5 详细设计中继续讨论。
2. 存量超限只做风险标记；是否在季度复盘中提示“可选整改建议”，留到 M7/M5 联动设计再定。
3. r006–r012 默认关闭项，是否在 MVP-2 根据复盘数据推荐开启，后续再定。
